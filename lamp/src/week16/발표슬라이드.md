# S0 · 표지

## 쿠키와 세션 — **무엇을 어디에 얼마나 오래 둘 것인가**

- 영화·드라마 리뷰 커뮤니티 (PHP · MariaDB)
- 받은 피드백 **셋** + 파다가 스스로 던진 질문 **셋**

> **결론부터** — 로그인은 **매 요청 다시 증명**하는 것이고,
> 그 증명에는 **등급**이 있으며, 언제든 **되돌릴 수** 있어야 한다.

# S1 · 로그인은 상태가 아니다

## HTTP는 상태가 없다 → **"로그인해 있다"를 담아둘 자리가 없다**

- 다만 **매 요청 비밀번호를 다시 대는 건 아니다**

```
로그인 순간    비밀번호로 증명   →  서버가 증거물(번호표)을 발급
그 뒤 매 요청   증거물 제시      →  서버가 발급 기록과 대조
```

> ### 그래서 물어야 할 것은 둘이다
> ### ① 매 요청 **무엇으로** 증명할 것인가?
> ### ② 그 증거물을 **어디에 어떻게 두고, 얼마나 오래 믿을** 것인가?

**➡️ ①의 답은 다음 장(S2), ②의 답은 S5다.**  *(그 사이 S3·S4가 ①이 남긴 약점을 실제로 고친 이야기)*

---

# S2 · ①의 답 — **뜻 없는 무작위 번호표**

> 다시 질문 — **매 요청 무엇을 들려 보낼 것인가?**

**후보는 사실상 둘뿐이다.**

- ① **아이디·비밀번호를 그대로** 매번 들려 보낸다
- ② 로그인할 때 발급한 **번호표 하나만** 들려 보낸다

**①은 안 된다.** 비밀번호가 **요청마다** 네트워크를 타고, 서버 로그에도 남는다.
**한 번만 새어도 계정 자체가 끝난다.**

**그래서 ②를 고른다** — 로그인에 성공한 순간 서버가 발급하는
**아무 뜻도 없는 긴 무작위 값**(`PHPSESSID`).

## 뜻이 없다는 것이 이 선택의 핵심이다

- 값 안에 아무 정보가 없으니 **고쳐봐야 소용없다** — `user_id=1` 을 `2` 로 바꾸는 식이 성립하지 않는다
- 번호표는 **서버에 있는 내 세션 한 줄을 찾는 열쇠**일 뿐이다
  — 누구인지·언제 로그인했는지는 **그 줄에** 적혀 있다 (그 줄을 어디에 두는지는 → S5)

## 대신 대가가 하나 따라온다 — **훔치면 그대로 통한다**

> 🎫 **지하철 표와 같다. 누가 들고 있든 통과시킨다.**
> 훔치면 비밀번호도 2단계 인증도 필요 없다 — 그 단계를 **뚫는** 게 아니라 **건너뛴다.**

- ★ 그래서 이 약점이 **뒤에 나오는 모든 결정의 출발점**이 된다 (S3 · S4)

# S3 · 쿠키만으로는 못 푸는 문제 — 그래서 **직접 만들었다**

## 이건 우리가 허술해서 생긴 문제가 아니다

> ### **쿠키만으로 로그인을 유지하는 한, 반드시 생긴다.**

> 📄 DBSC 설명서(W3C) — *"cookies … **only lend themselves to** bearer-token schemes"*

- ★ **쿠키가 나빠서가 아니다** — localStorage에 넣고 헤더로 보내도 **똑같다**
- 문제는 담는 그릇이 아니라 **"그대로 내밀면 통과하는 값"** 이라는 성질이다

## 해법은 하나 — **쿠키 말고 하나를 더** 쓴다 (기기 자체)

기기 안에 **꺼낼 수 없는 도장**을 새겨 두고, 서버가 매번 이렇게 시킨다.

```
서버   "아무 숫자나 하나 줄게. 그 도장으로 찍어서 보내봐"
기기   도장은 안 내주고, 찍은 자국만 보낸다
```

- 도장은 **기기 밖으로 절대 안 나온다** → **훔쳐갈 것 자체가 없다**
- 숫자가 매번 바뀌니 **자국도 매번 다르다** → **베껴놔도 다음번엔 안 통한다**
- *(업계에서는 이 도장 찍기를 **서명**이라고 부른다)*

## 좋은 생각이지만 — **두 번 실패했고, 세 번째가 올해 4월에 나왔다**

- **Token Binding**(2018) — 도장을 TLS 연결에 묶었다 → ★ **크롬이 Chrome 70에서 제거**(채택 부진)
- **WebCrypto로 직접** — 사이트마다 **도장 받는 구조를 설계**해야 했다 → **부담이 커서 안 퍼졌다**
- **DBSC** — 받는 지점을 **로그인 + 갱신 두 곳**으로 줄였다 → **Chrome 146 · 2026년 4월 정식**

> ### 그래서 **DBSC를 쓰는 대신, 같은 구조를 직접 만들었다.**
> DBSC는 자체 서명 인증서·TPM·프로토콜 직접 구현이 필요해 못 붙였다.
> 대신 **표준 API(WebCrypto)만으로 되는 축소판**을 짰다 — 구현은 다음 장.
> ※ 앞선 두 실패는 DBSC 설명서에 적힌 것이다 (출처 → 부록 S18)

# S4 · 만든 것 — **도장을 찍어야 연장된다**

## 도장 만들기 — 핵심은 **한 글자**다

```js
crypto.subtle.generateKey({ name: 'ECDSA', namedCurve: 'P-256' },
                          false,              // ★ extractable = false
                          ['sign', 'verify'])
```

- `false`면 **우리가 짠 JS로도 개인키를 못 읽는다** → **XSS가 나도 훔쳐갈 실체가 없다**
- IndexedDB에 넣어도 저장되는 건 값이 아니라 **손잡이**다 (쓸 수는 있고, 꺼낼 수는 없다)

## 흐름 — DBSC와 같은 모양

```
로그인 성공   도장 만들고 → 공개된 짝만 서버에 등록   /session/enroll.php
평소 요청     짧은 쿠키로 통과                        ← 빠르다
10분마다      도장 찍고 연장                          /session/refresh.php
```

- **왜 매 요청이 아닌가** — 도장 한 번이 **0.2~0.6초**(DBSC 실측). 매번 찍으면 못 쓴다
- ★ 만료 **1분 전에** 화면 뒤에서 미리 찍는다 → **사용자는 아무것도 못 느낀다**

## 무엇이 바뀌었나

```
전:  요청이 오면      연장   ← 훔친 쪽도 요청만 보내면 무기한
후:  도장을 찍어야    연장   ← 훔친 쪽은 10분이면 끊긴다
```

- ★ **훔치는 것 자체는 여전히 못 막는다.** 대신 **수명이 10분으로 못 박혔다**
- ★ 도장은 **갈아 끼울 수 없다**(`public_key IS NULL`일 때만 등록)
  → 훔친 세션으로 **자기 도장을 새로 심는** 길을 막는다

## 남긴 한계 — 먼저 말할 것

- **소프트웨어 도장이다** — TPM이 아니라 브라우저 저장소.
  악성코드가 브라우저 프로필을 통째로 복사하면 **도장도 같이 간다**
- **JS가 필요하다** — 쿠키 동의는 'JS 0줄'이 자랑이었는데 **여기서는 못 그런다**
- **등록 직전 몇 초**는 여전히 bearer다

# S5 · ②의 답 — **어디에 두고, 얼마나 오래 믿나**

## 어디에 — **번호표는 브라우저에, 그 내용은 서버에**

번호표를 쓰기로 했으면 **그 번호가 누구 것인지 적어둔 장부**가 어딘가엔 있어야 한다.
그 장부를 브라우저에 두면 **사용자가 직접 고칠 수 있다.** 그래서 장부는 서버에 둔다.

- 브라우저로 나가는 것은 **번호표 하나뿐**
- 누구인지·언제 로그인했는지는 **전부 서버 DB**(`sessions` 표)
- ★ 기준은 한 줄 — **고칠 수 있는 쪽에는 고쳐도 되는 것만 둔다**

## ★ 얼마나 오래 — **시계는 하나가 아니었다**

**처음엔 "30분" 같은 숫자 하나로 답하려 했다. 그게 틀렸다.**

- **유휴 시계** — 자리를 뜬 뒤 얼마 만에 끊나 *(쓰면 계속 밀린다)*
- **절대 상한** — 계속 써도 **언젠가는 반드시** 다시 묻는다
- **민감 동작** — 삭제·비번 변경 앞에서는 **그 자리에서** 다시 묻는다

**업계는 셋을 다 둔다**

- **OWASP** — 유휴 만료와 절대 만료를 **둘 다** 두라
- **NIST SP 800-63B** — 유휴 30분 / **절대 12시간**(AAL2), 낮은 등급도 30일 상한
- **GitHub** — 로그인해 있어도 위험한 설정 앞엔 `sudo` 모드

**우리 위치**

- 유휴 **✅ 20분** · 민감 동작 **✅ 15분 창** · 절대 상한 **△ 조건부**

> ⚠️ TTL 30분·유휴 20분은 **둘 다 마지막 사용 기준** → 쓰면 계속 밀린다(sliding).
> 전에는 **공격자가 20분마다 한 번씩만 요청해도 무기한 유지**됐다.
>
> ### ★ S4의 도장이 이 구멍을 메운다 — **미는 조건에 도장이 붙었다.**
> 도장 없는 쪽은 **아무리 요청해도 못 민다** → 훔친 쿠키의 수명이 **10분**으로 못 박힌다.
>
> 다만 **주인에게는 여전히 상한이 없다**(도장이 있으니 계속 밀린다).
> **다음에 넣는다면** — 로그인 시각을 적어두고 **12시간 넘으면 무조건 재인증**

# S6 · 나머지 두 축 + 그래서 바꾼 것

## 축 2 — 신뢰는 **켜짐/꺼짐이 아니라 등급이다**

- **CSRF는 '남의 사이트'를 막지만 '내 자리에 앉은 다른 사람'은 못 막는다**

```
비로그인   글 읽기
로그인     글쓰기 · 댓글 · 추천
재인증     영구삭제 · 비밀번호 변경 · 모든 기기 로그아웃
```

- ★ 등급을 **저장하지 않는다** — `auth_at`이 15분 안이냐로 판정
  - 저장하면 *"등급 2인데 user_id가 없는"* **모순**이 생긴다
  - 시각이라 **강등 코드가 없다 → 강등을 빠뜨릴 수도 없다**

## 축 3 — **되돌릴 수 있어야 한다**

- 훔치는 것 자체를 못 막으면, **"틀렸을 때 되돌릴 수 있는가"** 가 유일한 방어
- ★ **그래서 세션을 DB에 뒀다** — 파일이면 `WHERE user_id = ?` 를 못 쓴다

## 그래서 바꾼 것

- **자동 로그인 제거** — 증거물을 **30일 맡기던 것 → 아예 안 맡긴다**
- **요청마다 번호표 회전** — 증거물 하나의 수명을 **30초로**
- **브라우저 닫으면 소멸** — 자리를 뜨면 증거물도 사라진다
- ★ **기기 도장** — 증거물을 **연장하려면 도장이 필요하게** (S4)

```
전:  훔칠 수 있는 것 2개   PHPSESSID(30분) + remember(30일)
후:  훔칠 수 있는 것 1개   PHPSESSID — 그나마 도장 없으면 10분
```

# S7 · 로그인 방식 — 질문이 두 개인 줄 알았다

> 피드백: *"로그인 유지 — 로그인 방식에 대해 더 고민해보세요"*

- *"세션으로 유지가 맞나"* 와 *"자동 로그인이 맞나"* 를 **따로** 고민하고 있었다
- 본질로 내려가니 **같은 질문의 두 얼굴**이었다

**증명하는 방법은 근본적으로 셋뿐**

- ① 비밀을 **매번 보낸다** (HTTP Basic) → 매 요청이 유출 기회, 로그아웃 개념도 없다
- ② 증거물을 맡겨두고 매번 보낸다 (**bearer**) → **훔치면 끝** ← **우리 방식**
- ③ 비밀을 안 보내고 **안다는 증거만** 보낸다 → 패스키 · DBSC · mTLS **(→ S3·S4)**

> ★ **②와 ③의 차이는 "비밀을 전송하는가"** 다.

**그리고 세션과 자동 로그인은 같은 축 위의 점이었다**

```
        재증명 주기
        ├──────────────────────────────────────▶
    매 요청      30분        20분 유휴      30일
   (Basic)     세션 TTL     자동로그아웃   remember
```

> ### **"로그인 유지"는 기능이 아니라 재증명 주기를 늘리는 결정이다.**

# S8 · 로그인 방식 — 바꾼 것과 남긴 한계

**정문 — 로그인하는 순간**

- **시도 제한** (아이디+접속지) 5회 / 접속지 20회, 15분
  - ★ 아이디만 세면 **남의 계정을 일부러 잠글 수 있다**(계정 잠금 DoS)
  - ★ *'몇 번 틀렸나'는 공격자가 0으로 되돌리고 싶은 값* → 세션·쿠키가 아니라 **DB**
- **응답 시간 통일** — 아이디가 없어도 **더미 해시와 대조**
  - **메시지로는 계정 열거를 막았는데 시간으로 새고 있었다** (239ms vs 243ms)

**세션 — 로그인 이후**

- 권한이 바뀌는 **두 지점**에서 번호표 재발급 — 로그인 · **재인증**
  - ⚠️ 재인증을 빠뜨리고 있었다 → **주인이 문을 여는 순간 훔쳐간 열쇠도 같이 열린다**
- **요청마다 회전 + 옛 번호표 30초 유예**
  - 유예가 없으면 겹친 요청(연타·탭 두 개·F5)이 **몰살**
  - ★ 로그인·재인증은 **즉시 삭제** — 살려두면 훔쳐간 쪽이 그 30초를 쓴다
- **비번 변경 시 다른 세션 전부 폐기** · **'모든 기기에서 로그아웃'** 버튼
- **HTTPS 강제** — ★ `'secure' => !empty($_SERVER['HTTPS'])` 를 처음부터 써둬 **PHP는 한 줄도 안 고쳤다**

**남긴 한계 — 발표에서 스스로 말할 것**

- **세션 쿠키를 훔치면 여전히 그 사람이 된다** (bearer 모델의 성질)
  · 다만 **도장이 없으면 10분이면 끊긴다** (→ S4)
- **주인에게는 절대 상한이 없다** (→ S5)
- **새 기기 알림의 사각지대** — 이건 '로그인'을 잡는다. **쿠키를 붙여넣으면 로그인이 없어 안 잡힌다**

---

# S9 · 자동 로그인을 **만들었다가 없앴다**

> 피드백: *"자동 로그인 remember — 왜 쿠키로 사용했는가, 보안 문제는 없는가"*

- 교과서대로 만들었다 — 쿠키엔 무작위 토큰, DB엔 지문(SHA-256), 쓸 때마다 회전
- 그런데 질문은 결국 하나였다 → **"훔치면 남이 내 계정을 쓸 수 있는 것 아닌가?"**
- **답은 '그렇다'** — 훔치면 **비밀번호도 2단계 인증도 필요 없다.** 그 단계를 **건너뛴다**

**막아봤지만 셋 다 부족했다**

- `HttpOnly`·`SameSite`·`Secure` → 기회는 줄지만 **없어지지 않는다**
- 토큰 회전 → 수명은 줄지만 **여전히 유효하다**
- **재사용 탐지**(계열, Jaspan 패턴) → ★ **주인이 그 자리로 돌아와야 작동한다**
  - 그 브라우저를 며칠 안 켜면 안 걸리고, **새로 로그인해도 도난당한 계열은 그대로 산다**

> ### 그릇을 바꾸는 대신 **'맡기지 않기'** 를 골랐다
> `remember_tokens` 표 삭제 · `remember.php` 삭제 · '로그인 유지' 체크박스 제거

- **30일 → 20~30분.** 해결이 아니라 **축소**다
- ★ **곁가지로 예외가 하나 사라졌다** — 로그인하는 길이 비밀번호 하나뿐이 되면서
  *"쿠키로 되살아난 세션은 재인증 창을 안 열어준다"* 는 특례가 통째로 없어졌다
  > **코드가 짧아진 게 아니라 생각할 게 줄었다.**
- **남긴 한계** — 올 때마다 로그인해야 한다. **은행이 정확히 이 선택을 한다**

# S10 · 쿠키 동의 — 그 앞에 질문이 하나 더 있었다

> 피드백: *"동의를 받고 나서 **어디에 저장해야 할지** 고민해보시길"*

> ### **"이게 애초에 동의여야 하나?"**

- 우리 배너는 `[확인]` 버튼 하나짜리 **안내**였다
- 값은 `cookie_notice=1` 하나 → **무엇에 동의했는지가 없었다**
- **저장 위치를 고민하기 전에 동의 형식으로 바꾸는 것이 먼저**였다

**근거 ① — 우리가 심는 쿠키에 두 무리가 섞여 있었다**

- 사용자가 **시킨 것** — 정렬 탭(`pref_sort`), '로그인 유지' → **알려주면 된다**
- 우리가 **알아서 쌓는 것** — 검색어, 읽은 글 → **쌓이는 줄도 모른다. 물어봐야 한다**
- 배너 문구가 이미 자백하고 있었다 — *"**최근 본 글**을 기억하려고"* 라고 써놓고 확인만 받았다

**근거 ② — 확인과 동의는 '되돌릴 수 있는가'로 갈린다**

- **확인** = 읽었다는 표시, 되돌릴 게 없다 / **동의** = 허락, **언제든 거둘 수 있어야**

> ### **거절할 수 없으면 물어본 게 아니다.**

**근거 ③ — 법과 업계가 같은 말을 한다**

- **GDPR 7조 1항** — 입증 책임이 **사업자에게** → 증거를 상대방 손(쿠키)에 맡기면 증거가 아니다
- **CNIL 제재(2021년 12월 말)** — Google €1.5억 · Facebook €6천만,
  사유는 **"거절이 수락만큼 쉽지 않았다"**

# S11 · 쿠키 동의 — 갖춰야 할 다섯

- ① **거절할 수 있다** — `[모두 동의] [선택한 것만] [거절]` 을 **같은 무게**로
- ② **항목별로 고른다** — 열람 기록 / 검색 기록 따로 *(검색어가 더 민감하다)*
- ③ **철회할 수 있다 — 비회원도** (`/cookies.php`)
  - `settings/` 안에 두지 않았다 — **받을 때보다 거둘 때 문턱이 높으면 안 된다**
- ④ **동의 전엔 안 심는다** — *모르면 안 심는다*가 기본값
- ⑤ **증빙이 남는다** — `consent_log` (**고치지 않고 쌓기만**)
  - **철회도 새 줄**로 — *'동의했다가 철회함'* 과 *'동의한 적 없음'* 은 **다른 사실**

**그리고 심는 주체가 바뀌었다**

- `cookie_notice`는 **유일하게 JS가 직접 심던 쿠키**였다
- **서버가 모르는 동의는 증명할 수 없어서** 폼 POST로 → **JS 0줄**, `httponly` 켬

**결과 — 같은 사실이 두 군데, 역할이 다르다**

```
쿠키          "배너 띄울까? 이 쿠키 심어도 되나"   ← 판단용 캐시
consent_log   언제 · 무엇에 · 어떤 방침 버전에      ← 증빙 원본
```

> **쿠키가 사라져도 사실은 안 사라진다.** 그게 이 구조의 전부다.

> ★ **판단 기준이 하나 늘었다** — *"지금 동작에 필요한가"* vs **"나중에 증명해야 하는가."**
> 같은 축에 로그인 이력·결제·약관 동의가 걸린다. **전부 DB다.**

# S12 · 조회수 — 한 단어를 파니 여섯이 나왔다

> 피드백: *"조회수 중복 방지 — **시간**에 대해서 고민해보세요"*

- ① **다시 세는 기준이 아예 없었다** — `$_SESSION['viewed_posts'] = [12, 9, 3]` ← **시각이 없다**
  - **세션 수명(유휴 20분)이 그 정책을 우연히 대신 정하고** 있었다
  - → **결정한 적 없는 값이 정책이 되어 있었다**
- ② **기준을 만들었더니 시간대가 어긋났다** — DB는 UTC, PHP는 KST
  - **"하루에 한 번"의 '하루'가 자정이 아니라 오전 9시**부터였다
- ③ **조회수를 쓰는 쪽도 시간을 안 봤다** — '지금 뜨는 글'이 누적 조회수라 **1년 전 글이 영원히 1등**
  - **이름은 '지금 뜨는'인데 동작은 '역대 많이 본'**
- ④ **한 사람이 두 번 세어졌다** — 첫 요청은 `i:<IP>`, 둘째는 `d:<기기>` → **모든 신규 방문자**
- ⑤ **쿠키만 지우면 부풀릴 수 있었다** — 조회수는 홈 '지금 뜨는 글'·'인기' 탭·랭킹을 움직인다
  - ⚠️ **그리고 ③의 개선이 이 구멍을 키웠다** — 누적 5,000을 이기는 데 **열 번이면 충분**해졌다
- ⑥ **정렬 기준과 표시 숫자가 달랐다** — **조회 502가 조회 1497보다 위에** 떴다

# S13 · 조회수 — 실무를 보고 바꾼 것

**레퍼런스**

- **Discourse** — `topic_views` 표, `viewed_at`이 **DATE**(하루 1회),
  로그인은 user_id / 아니면 IP, **Redis를 문지기**로
- **django-hitcount** — 창이 **설정값**(기본 7일), 세션키+IP+UA로 판정

> **공통점 셋** — ① 기간이 **숫자로 코드에** ② 세션이 아니라 **표** ③ 판정 키가 **여러 단계**
> **우리에게 없던 것이 정확히 이 셋이었다.**

**바꾼 것**

```sql
post_views ( post_id · viewer_key · ip_hash · viewed_on DATE )
PRIMARY KEY (post_id, viewer_key)
```

- **판정·기록을 UPSERT 한 방** — 영향 행 `1`·`2`=센다 / `0`=오늘 이미 봄
  - *"조회해서 보고 없으면 넣기"* 로 나누면 그 사이에 끼어들어 두 번 세어진다
- **판정 키 2단** — `u:<회원번호>` / `d:<기기번호>`
  - Discourse의 IP 자리에 **device 쿠키**를 넣었다 — **IP는 공유되지만** 쿠키는 브라우저마다 하나
  - ★ **새 식별자를 안 만들었다** — 기기 목록용으로 심어둔 쿠키를 그대로 쓴다
- **쿠키가 없던 요청에만** 접속지 지문도 확인 → 쿠키 삭제·시크릿 창 차단
  - ★ **오탐 범위를 좁혔다** — 항상 IP로 판정하면 같은 건물이 통째로 한 명
  - ★ **로그인 사용자의 IP는 안 담는다** — **필요 없는 개인정보는 안 모은다**
- **봇은 아예 안 센다** — 세션도 안 만든다
- **날짜는 PHP에서 계산해 넘긴다** — 시각 계산은 **한쪽 세계 안에서만**

**남긴 한계**

> '지금 뜨는 글'을 최근 기준으로 바꾸자 부풀리기가 **오히려 쉬워졌다.**

# S15 · 세션이 하나만 있는 게 맞는가

> 피드백이 아니라 **앞의 결정들을 하다 스스로 던진 질문.** 여기서 기준 하나가 나왔다.

**갈래 A — 한 사람에게 세션이 하나여야 하나**

- 한 계정 한 세션으로 만들었다가 **되돌렸다**

```
한 곳만   훔친 세션이 재로그인 한 번에 쫓겨남 · 대신 PC+폰 동시 사용 불가
여러 곳   편한데, 훔친 세션이 '내 기기 중 하나'로 숨음
```

- **여러 곳을 허용하려면 볼 수 있게 해줘야 한다** — 그게 **기기 목록**이다
- 네이버·구글이 여러 기기를 허용하는 것도 **'내 기기 목록'을 주기 때문**
- → **"여러 곳 허용 + 기기 목록"** 을 골랐다

**갈래 B — 세션 하나에 성격이 다른 값 넷을 담는 게 맞나**

- `csrf_token` 거의 안 바뀜 · `user_id` 안 바뀜 · `auth_at` 가끔 · `last_seen` **매 요청**
- **바뀌는 빈도는 극단적으로 다르지만, 넷 다 "이 방문" 동안만 살면 된다**
- → **나누지 않는 게 맞다**

# S16 · 그래서 나온 기준 한 줄

**실제로 나눈 것**

- 기기 목록 → `user_devices` 분리 — 세션은 30분, **기기 기록은 계속 살아야**
- 조회 기록 → `post_views` 분리 — 세션은 요청마다, **조회는 가끔**
- 동의 증빙 → 쿠키 + `consent_log` — **나중에 증명해야**

**그대로 합쳐 둔 것** — 세션 네 값 *(수명이 같고 함께 읽고 쓴다)*

> ### **수명과 주인이 같으면 합치고, 다르면 나눈다.**

- **나눈다** — 수명이 다를 때 · 접근 패턴이 다를 때 · 주인이 다를 때 · **나중에 증명해야 할 때**
  - 판정용과 증빙용은 **보관 기간이 반대다** (`login_attempts` 15분 vs `consent_log` 영구)
- **합친다** — 수명이 같을 때 · 함께 읽고 쓸 때 · **다른 값에서 계산되는 것은 저장하지 않는다**

**남긴 한계 — 합치는 대가**

- 📂 `auth.php` 주석: *"**auth_at까지 같이 갱신하면 sudo 창이 영원히 안 닫힌다**"*
  → **한 그릇에 담으면 하나를 만지다 옆을 건드리기 쉽다**
- 중복 하나를 **발견했지만 두기로 했다** — `$_SESSION['last_seen']`(인증 정책) vs
  `sessions.last_active`(저장소 사정). 합치면 **저장소를 파일로 바꿀 때 유휴 타임아웃이 깨진다**
  > **중복이 항상 나쁜 건 아니다.** *"우연히 같은 값"* 과 *"본질적으로 같은 값"* 은 다르다

# S17 · 마무리

> ### **로그인은 매 요청 다시 증명하는 것이고,**
> ### **그 증명에는 등급이 있으며,**
> ### **언제든 되돌릴 수 있어야 한다.**

**세션·쿠키·DB를 어디에 쓸지는 전부 이 문장에서 나왔다.**

**막을 수 없는 것은 인정하고, 목표를 바꿨다**

- **짧게** — 자동 로그인 제거 · 요청마다 회전 → 30일 → **20~30분**
- **얕게** — 재인증(sudo) → ★ **쿠키를 훔쳐도 계정 자체는 못 뺏는다**
- **보이게** — 기기 목록 · 새 기기 로그인 알림
- ★ **묶이게** — 기기 도장이 있어야 연장 (DBSC 축소판, S4)

**스스로 말하는 한계**

- bearer 모델이라 **훔치는 것 자체는 못 막는다** — 대신 **수명을 10분으로** 못 박았다
- 그 도장은 **소프트웨어 도장**이다 — 하드웨어(TPM)가 아니라 브라우저 저장소
- **주인에게는 절대 상한이 없다** — 다음에 넣는다면 **12시간**
- 조회수는 **다른 네트워크 + 쿠키 삭제**면 뚫린다

> ★ 이번에 얻은 것은 기능이 아니라 **판단 기준 셋**이다 —
> **"고쳐서 이득을 보나"** · **"값의 주인이 누구인가"** · **"나중에 증명해야 하는가"**

# S18 · 부록 — 출처

> 발표 중에 띄울 장은 아니다. **"그거 어디서 봤냐"** 는 질문이 나올 때만 연다.

**세션을 기기에 묶는 방향 (S3·S4) — 문서에 적힌 것**

- **DBSC 설명서** — [w3c/webappsec-dbsc](https://github.com/w3c/webappsec-dbsc)
  · *"they only lend themselves to **bearer-token schemes**"* (문제 정의)
  · *"DBSC is not the first proposal in this space, with notable others
  **Token Binding** and **WebCrypto**"* (앞선 시도)
- **Token Binding** — [RFC 8471](https://www.rfc-editor.org/rfc/rfc8471.html) (2018-10)
  · 크롬 제거는 [Intent to Remove: Token Binding](https://groups.google.com/a/chromium.org/g/blink-dev/c/OkdLUyYmY1E) — **Chrome 70에서 제거, 사유는 채택 부진**
- **DBSC 출시** — [구글 보안 블로그](https://blog.google/security/protecting-cookies-with-device-bound-session-credentials/) ·
  [Workspace 업데이트](https://workspaceupdates.googleblog.com/2026/05/prevent-account-takeovers-with-DBSC-now-generally-available-in-the-Chrome-browser-for-Windows.html)
  · **Chrome 146 · 2026년 4월 윈도우 GA**(TPM), macOS는 147(Secure Enclave)
