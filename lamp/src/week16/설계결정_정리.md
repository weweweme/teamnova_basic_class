# 설계 결정 정리 — 피드백에서 시작한 여섯 갈래

> 받은 피드백 셋과, 그것을 파다가 스스로 던진 질문 셋을 정리한 문서.
> 각 항목은 **무엇이 문제였나 → 무엇을 했나 → 왜 → 남은 한계** 순서다.

# 1. 로그인에 대한 철학

## 축 1 — **로그인은 상태가 아니라 계속되는 증명이다**

```
HTTP는 상태가 없다 → "로그인해 있다"는 상태는 존재하지 않는다
                     → 매 요청마다 다시 증명하는 것뿐이다
```

**여기서 나머지가 전부 파생됐다.**

- 세션 30분 · 유휴 20분 · 자동 로그인 제거 → 전부 **"재증명 주기를 얼마로 할까"의 답**
- 요청마다 번호표 회전 → **증명의 유효기간을 짧게**
- 브라우저 닫으면 소멸 → **자리를 뜨면 증명도 끝**

## 축 2 — **신뢰는 켜짐/꺼짐이 아니라 등급이다**

```
비로그인   글 읽기
로그인     글쓰기 · 댓글 · 추천
재인증     영구삭제 · 비번 변경 · 기기 끊기
```

> **CSRF는 '남의 사이트'를 막지만 '내 자리에 앉은 다른 사람'은 못 막는다.**
> 세션은 '이 브라우저가 로그인했다'까지만 증명한다.

★ 이 덕에 **쿠키를 훔쳐도 계정 자체는 못 뺏는다.** 비번 변경이 막혀 있으니까.

## 축 3 — **되돌릴 수 있어야 한다**

```
로그아웃      → 세션 행 삭제
기기 끊기     → 그 기기의 세션까지
비번 변경     → 다른 세션 전부 폐기
동의 철회     → 쌓인 쿠키까지 삭제
```

> ★ **그래서 세션을 DB에 뒀다.** 파일이면 `WHERE user_id = ?` 를 못 쓴다.
> *"나중에 취소할 수 있는가"* 가 저장소를 고른 진짜 이유다.

## 그리고 인정한 것 — **막을 수 없는 게 있다**

```
쿠키를 훔치면 그 사람이 된다   ← bearer 모델의 성질
```

**목표를 "막기"에서 "짧게, 얕게, 눈에 보이게"로 바꿨다.**

- **짧게** — 30일 → 20~30분
- **얕게** — 계정은 못 뺏음 (재인증)
- **보이게** — 기기 목록 · 새 기기 알림

## 한 문장으로

> ### **로그인은 매 요청 다시 증명하는 것이고,**
> ### **그 증명에는 등급이 있으며,**
> ### **언제든 되돌릴 수 있어야 한다.**

**세션·쿠키·DB를 어디에 쓸지는 전부 이 문장에서 나왔다.**

> ➡️ **아래 다섯 갈래는 이 문장이 어떻게 나왔는지의 기록이다.**
> 순서대로 읽으면 **큰 원칙 → 구체적인 결정 → 그 결정에서 뽑아낸 기준**으로 이어진다.

# 2. 로그인 방식에 대한 고찰 — 결론과 바꾼 구현

> 피드백: *"로그인 유지 — 로그인 방식에 대해 더 고민해보세요"*

## 본질로 되돌아가면

**HTTP는 상태가 없다. "로그인해 있다"는 상태는 존재하지 않는다.**

> 존재하는 건 **매 요청마다 다시 증명하는 것**뿐이다.

그러면 질문이 바뀐다 — *"어떻게 상태를 유지하나"* 가 아니라 **"매 요청 무엇으로 증명하나."**

## 증명하는 방법은 근본적으로 셋

| | 방식 | 문제 |
|---|---|---|
| ① | 비밀을 매번 보낸다 (HTTP Basic) | 매 요청이 유출 기회. 로그아웃 개념이 없다 |
| ② | **증거물을 맡겨두고 매번 보낸다 (bearer)** | **훔치면 끝** ← 우리 방식 |
| ③ | 비밀을 안 보내고 **안다는 증거만** 보낸다 | 패스키·DBSC·mTLS |

> ★ **②와 ③의 차이는 "비밀을 전송하는가"** 다.

## ★ 그래서 세션과 자동 로그인은 **같은 축 위의 점**이었다

```
        재증명 주기
        ├──────────────────────────────────────▶
    매 요청      30분        20분 유휴      30일
   (Basic)     세션 TTL     자동로그아웃   remember
```

**"로그인 유지"는 기능이 아니라 재증명 주기를 늘리는 결정**이다.
→ *"세션이 맞나 / remember가 맞나"* 는 **같은 질문의 두 얼굴**이었다.

## 바꾼 구현

**정문 (로그인하는 순간)**
- **시도 제한** — (아이디+접속지) 5회 / 접속지 20회, 15분
  · ★ **아이디만 세면 남의 계정을 일부러 잠글 수 있다**(계정 잠금 DoS) → 조합으로 센다
  · ★ **'몇 번 틀렸나'는 공격자가 0으로 되돌리고 싶은 값**이라 세션·쿠키가 아니라 **DB**
- **응답 시간 통일** — 아이디가 없어도 **더미 해시와 대조**한다
  · bcrypt(cost 12)는 일부러 느려서, 안 부르면 응답이 훨씬 빨랐다
  · **메시지로는 계정 열거를 막았는데 시간으로 새고 있었다.** 재보니 239ms vs 243ms로 같아졌다
  · ★ **CSRF의 `hash_equals`와 같은 이야기** — 비교할 땐 **걸리는 시간까지** 같아야 한다

**세션 (로그인 이후)**
- **권한이 바뀌는 두 지점에서 번호표 재발급** — 로그인 · **재인증**
  · ⚠️ 재인증 쪽을 빠뜨리고 있었다 → **주인이 문을 여는 순간 훔쳐간 열쇠도 같이 열린다**
- **요청마다 회전 + 옛 번호표 30초 유예**
  · 유예가 없으면 겹친 요청(링크 연타·탭 두 개·F5·fetch)이 **몰살**한다
  · ★ 로그인·재인증은 즉시 삭제 — **거기서 살려두면 훔쳐간 쪽이 그 30초를 쓴다**
  · **같은 '회전'인데 왜 도는지가 달라서** 옛것을 살리고 죽이고가 갈린다
- **비번 변경 시 다른 세션 전부 폐기**
  · *"털린 것 같은데?"* 에 사람이 제일 먼저 하는 행동인데 **공격자가 그대로 남아 있었다**

**기기**
- `user_devices` 표 + 새 기기 로그인 알림 + 기기별 끊기
- ★ **여러 곳 허용과 기기 목록은 짝이다** — 목록 없이 여러 곳을 허용하면
  훔친 세션이 *'내 기기 중 하나'* 로 숨어 아무도 눈치채지 못한다

**채널**
- **HTTPS** + http는 302로 차단
  · ★ `'secure' => !empty($_SERVER['HTTPS'])` 를 처음부터 써둬서 **PHP 코드는 한 줄도 안 고쳤다**

## 남긴 한계 — 발표에서 스스로 말할 것

- **세션 쿠키를 훔치면 여전히 그 사람이 된다** — bearer 모델의 성질
- **세션 절대 상한이 없다** — 유휴 20분은 *"아무도 안 쓰면"* 끊는 것이라,
  공격자가 20분마다 한 번씩 요청하면 **무기한 유지**된다 (알고도 넘어간 지점)
- **비밀번호 최소 4자** — 임시 계정 환경이라 그대로 뒀다
- **새 기기 알림의 사각지대** — 이건 '로그인'을 잡는다.
  **세션 쿠키를 훔쳐 붙여넣으면 로그인이 없어 안 잡힌다.** 비밀번호 유출엔 강하고 세션 탈취엔 약하다

## 검토했지만 안 한 것

- **DBSC** — 쿠키를 기기 개인키에 묶는 표준(Chrome 146, 2026-04 정식).
  HTTPS는 붙였지만 **자체 서명 인증서·JWT 검증 직접 구현**이 필요하고,
  ★ **제가 검증할 수 없다** — 크롬+TPM이 있어야 하고, **안 붙어도 사이트는 멀쩡히 돌아간다**
- **패스키** — 로그인 순간만 지킨다. **로그인 이후는 여전히 쿠키**라 이번 주제에 답이 안 된다
- **주기적 회전(5분)** — 유휴가 20분이라 줄어드는 폭이 작고, 유예를 두면 탐지가 무뎌진다

# 3. 자동 로그인을 없앤 이유

> 피드백: *"자동 로그인 remember — 왜 쿠키로 사용했는가, 보안 문제는 없는가"*

## 처음엔 교과서대로 만들었다

- 쿠키엔 **무작위 토큰**, DB엔 **지문(SHA-256)** — 신원은 절대 안 담는다
- 쓸 때마다 **새것으로 회전**(rotation)
- 만료를 **양쪽에** — 쿠키 만료는 브라우저가 지키는 약속이라 사용자가 늘릴 수 있다

## 그런데 질문은 결국 하나였다

> **"쿠키를 훔치면 남이 내 계정을 쓸 수 있는 것 아닌가?"**

**답은 '그렇다'.** 우리 인증은 **bearer(소지자) 토큰**이다.

> 🎫 **지하철 표와 같다. 누가 들고 있든 통과시킨다.**
> 훔치면 **비밀번호도 2단계 인증도 필요 없다** — 그 단계를 뚫는 게 아니라 **건너뛴다.**

## 막아본 것 셋 — 그리고 왜 부족했나

| 시도 | 결과 |
|---|---|
| `HttpOnly`·`SameSite`·`Secure` | 기회는 줄지만 **없어지지 않는다** |
| 토큰 회전 | 수명은 줄지만 **여전히 유효하다** |
| **재사용 탐지**(계열 `series`) | ★ **주인이 그 자리로 돌아와야 작동한다** |

**재사용 탐지까지 실제로 만들어 봤다.** 폐기된 토큰이 다시 나타나면 복제된 것이므로 전부 끊는 방식(Jaspan 패턴). 그런데 —

- 주인이 **그 브라우저를 한동안 안 켜면** 며칠이 지나도 안 걸린다
- 비밀번호로 **새로 로그인해도 도난당한 계열은 그대로 산다**

→ **완화는 되지만 해결은 안 된다.** 우리 구현의 결함이 아니라 **모델의 성질**이다.

## 그래서 '맡기지 않기'를 골랐다

```
전:  훔칠 수 있는 것 2개   PHPSESSID(30분) + remember(30일)
후:  훔칠 수 있는 것 1개   PHPSESSID(30분, 브라우저 닫으면 소멸)
```

- **30일 → 20~30분.** 해결이 아니라 **축소**다
- 세션 쿠키는 만료 시각이 없어 **브라우저를 닫으면 사라진다**
  → *"창을 닫으면 로그아웃"* 은 **원래부터 그랬다.** 안 풀리던 이유는 `remember` 하나뿐이었다

## 잃은 것도 명확히

**올 때마다 로그인해야 한다.** 편의를 내주고 위험을 줄인 거래이고, **은행이 정확히 이 선택을 한다.**

## 곁가지 — 지우니까 예외가 사라졌다

로그인하는 길이 **비밀번호 하나뿐**이 되면서,
*"쿠키로 되살아난 세션은 재인증 창을 안 열어준다"* 는 **특례가 통째로 없어졌다.**

> **코드가 짧아진 게 아니라 생각할 게 줄었다.**

## 💬 발표 대사

> *"자동 로그인을 **만들었다가 없앴습니다.** 30일짜리 열쇠를 사용자 PC에 맡기는 건데,
> 훔치면 비밀번호도 2단계 인증도 없이 30일간 그 사람이 되거든요."*
> *"**탐지까지 만들어봤는데, 탐지는 주인이 그 자리로 돌아와야 작동**하더군요.
> 그래서 **애초에 맡기지 않는 쪽**을 골랐습니다."*

# 4. 쿠키 안내 확인을 어떻게 처리했나

> 피드백: *"동의를 받고 나서 **어디에 저장해야 할지** 고민해보시길"*

## ★ 그 앞에 질문이 하나 더 있었다

> **"이게 애초에 동의여야 하나?"**

우리 배너는 `[확인]` 버튼 하나짜리 **안내**였다. 저장 위치를 고민하기 전에 **동의 형식으로 바꾸는 것**이 먼저였다.

## 답은 우리가 심는 쿠키 목록에 있었다

| 사용자가 **시킨 것** | 우리가 **알아서 쌓는 것** |
|---|---|
| 정렬 탭을 눌렀으니 기억 (`pref_sort`) | 검색어가 남는다 (`recent_search`) |
| '로그인 유지' 체크 (`remember`) | 무엇을 읽었는지 (`recent_posts`) |
| → **알려주면 된다** | → **쌓이는 줄도 모른다. 물어봐야 한다** |

> 배너 문구가 이미 자백하고 있었다 — *"**최근 본 글**을 기억하려고"* 라고 써놓고 확인만 받았다.

## 확인과 동의의 결정적 차이 — **되돌릴 수 있는가**

- **확인** = '읽었다'는 표시. 되돌릴 게 없다
- **동의** = 허락. **언제든 거둘 수 있어야 한다**

> **거절할 수 없으면 물어본 게 아니다.**

## 갖춘 것 다섯 — 하나라도 빠지면 동의가 아니다

- ① **거절할 수 있다** — `[모두 동의] [선택한 것만] [거절]`
- ② **항목별로 고른다** — 열람 기록 / 검색 기록 따로
  *(검색어는 사람이 무엇을 궁금해했는지 그 자체라 더 민감하다)*
- ③ **철회할 수 있다** — **비회원도.** `/cookies.php`
  → `settings/` 안에 두지 않았다. **받을 때보다 거둘 때 문턱이 높으면 안 된다**
- ④ **동의 전엔 안 심는다** — *모르면 안 심는다*가 기본값
- ⑤ **증빙이 남는다** — `consent_log` (**고치지 않고 쌓기만**)

## 그래서 같은 사실이 두 군데 — 역할이 다르다

```
쿠키          "배너 띄울까? 이 쿠키 심어도 되나"   ← 판단용 캐시
consent_log   언제 · 무엇에 · 어떤 방침 버전에      ← 증빙 원본
```

> **증거는 증명하려는 사람 손에 있어야 한다.** 쿠키는 사용자가 지울 수 있다.
> **철회도 새 줄로 남긴다** — *'동의했다가 철회함'* 과 *'동의한 적 없음'* 은 **다른 사실**이다.

## 근거

- **GDPR 7조 1항** — *"controller shall be able to demonstrate that the data subject has consented"*
  **입증 책임이 사업자에게 있다**
- **GDPR 7조 3항** — 철회는 동의만큼 쉬워야 한다
- **CNIL 제재(2021-12-31)** — Google €1.5억 · Facebook €6천만.
  사유는 **"거절이 수락만큼 쉽지 않았다"** (수락 1클릭 vs 거절 3~5클릭)
  → 그래서 세 버튼을 **같은 무게**로 뒀다. 거절을 흐리게 하는 건 **유도**다
- **Cookiebot(상용 CMP)** — Consent ID·시각·User agent·동의 상태를 **서버에** 남기고 **같은 값을 쿠키에도** 둔다
  → **우리가 만든 것과 같은 구조**였다

## ★ 우리 판단 기준이 못 잡은 것

기준 둘(*"고쳐서 이득을 보나"* / *"값의 주인이 누구인가"*)은 전부 **"지금 이 요청이 도는가"** 만 본다.
동의는 **1년 뒤에 증명해야 하는 값**이었다.

> **세 번째 축이 필요했다 — "지금 동작에 필요한가" vs "나중에 증명해야 하는가."**
> 같은 축에 로그인 이력·결제·약관 동의가 걸린다. **전부 DB다.**

## 곁가지

`cookie_notice`는 **우리 사이트에서 유일하게 JS가 직접 심던 쿠키**였다.
동의로 바뀌며 그게 문제가 됐다 — **서버가 모르는 동의는 증명할 수 없다.**
→ 폼 POST로 바꿨다. **JS가 한 줄도 없고** `httponly`도 켰다.

# 5. 바뀐 조회수 중복 방식 — 무엇을, 왜

> 피드백: *"조회수 중복 방지 — **시간**에 대해서 고민해보세요"*

## 한 단어에서 문제 여섯이 나왔다

**① 다시 세는 기준이 아예 없었다**

```php
$_SESSION['viewed_posts'] = [12, 9, 3]   // ← 시각이 없다
```

*"몇 시간 뒤에 다시 셀까"* 를 정할 방법 자체가 없었고,
**세션 수명(유휴 20분)이 그 정책을 우연히 대신 정하고** 있었다.
→ **결정한 적 없는 값이 정책이 되어 있었다.**

게다가 세션 쿠키는 브라우저를 닫으면 사라져 **창을 껐다 켜면 다시 세어졌다.**
F5 연타는 막았는데 정작 부풀리기는 쉬웠다.

**② 기준을 만들었더니 시간대가 어긋나 있었다**

```
DB   12:53 (UTC)      CURDATE() 를 쓰면
PHP  21:53 (KST)      하루의 경계가 자정이 아니라 오전 9시
```

밤 11시에 본 글을 **새벽 1시에 다시 봐도 안 세어졌다.**
→ **"하루에 한 번"이라고 정해놓고 그 '하루'가 우리가 아는 하루가 아니었다.**

**③ 조회수를 쓰는 쪽도 시간을 안 봤다**

'지금 뜨는 글'을 **누적 조회수**로 뽑고 있었다 → **1년 전 글이 영원히 1등.**
**이름은 '지금 뜨는'인데 동작은 '역대 많이 본'** 이었다.

**④ 한 사람이 두 번 세어졌다**

IP를 대체 키로 넣었더니 — 첫 요청은 쿠키가 없어 `i:<IP>`, 둘째 요청은 쿠키가 생겨 `d:<기기>`.
**모든 신규 방문자에게 생기는 일**이었다.

**⑤ 조회수가 첫 화면을 결정하는데 쿠키만 지우면 부풀릴 수 있었다**

조회수는 표시만 되는 숫자가 아니다 — 홈 '지금 뜨는 글' · 게시판 '조회'/'인기' 탭 · 랭킹.
⚠️ **그리고 ③의 개선이 이 구멍을 키웠다** — 누적 5,000을 이기는 데 **열 번이면 충분**해졌다.

**⑥ 정렬 기준과 표시 숫자가 달랐다**

정렬은 최근 7일인데 화면엔 누적을 찍어서 **조회 502가 조회 1497보다 위에** 떴다.

## 실무 조사 — 근거로 삼은 것

- **Discourse** — `topic_views` 표, `viewed_at`이 **DATE**(하루 1회),
  로그인은 user_id / 아니면 IP, **Redis를 문지기**로 앞에 둔다
- **django-hitcount** — 창이 **설정값**(기본 7일), 세션키+IP+UA로 판정
- **공통점 셋**: ①**창이 숫자로 코드에 있다** ②세션이 아니라 **표** ③판정 키가 **여러 단계**

> **우리에게 없던 것이 정확히 이 셋이었다.**

## 만든 것

```sql
post_views ( post_id · viewer_key · ip_hash · viewed_on DATE )
PRIMARY KEY (post_id, viewer_key)
```

- **판정·기록을 UPSERT 한 방** — 영향 행 `1`·`2`=센다 / `0`=오늘 이미 봄
  → *"조회해서 보고 없으면 넣기"* 로 나누면 그 사이에 끼어들어 두 번 세어진다
- **판정 키 2단** — `u:<회원번호>` / `d:<기기번호>`
  · Discourse의 IP 자리에 **device 쿠키**를 넣었다. **IP는 공유되지만**(회사망) 쿠키는 브라우저마다 하나
  · ★ **새 식별자를 안 만들었다** — 기기 목록에 쓰려고 심어둔 쿠키를 그대로 쓴다
- **쿠키가 없던 요청에만 접속지 지문도 함께** 확인 → 쿠키 삭제·시크릿 창 차단
  · ★ **오탐 범위를 좁혔다** — 항상 IP로 판정하면 같은 건물이 통째로 한 명.
    우리는 **공유 IP의 다른 사람이 '처음 여는 글 하나'만** 누락된다
  · ★ **로그인 사용자의 IP는 안 담는다** — 회원 번호로 충분. **필요 없는 개인정보는 안 모은다**
    (Discourse 소스에도 같은 주석이 있다)
- **봇은 아예 안 센다** — 세션도 안 만든다
- **날짜는 PHP에서 계산해 넘긴다** — 시각 계산은 **한쪽 세계 안에서만**

## '지금 뜨는 글'도 함께 고쳤다

- **최근 7일 조회수 순** — `post_views`에 날짜가 남아 비로소 가능해졌다
- **같은 표가 '중복 방지'와 '최근 인기'를 동시에** 떠받친다
- **판정은 하루, 집계는 7일** — **쓰임이 다르면 기간도 다르다**
- 화면 숫자도 **정렬 기준에 맞췄다** → ★ **줄마다, 그 줄의 순서를 결정한 숫자를 보여준다**

## 남긴 한계

- 다른 네트워크 + 쿠키 삭제 → 뚫린다.
  막으려면 **브라우저 지문 채취**인데 **우리가 만든 동의 기능과 앞뒤가 안 맞는다**
- 로그인 전환 시 한 번 더 센다 (Discourse도 동일)
- 공유 IP의 다른 사람이 **처음 여는 글 하나**만 누락

## ★ 이번 작업의 수확

> **개선이 다른 쪽 구멍을 키운다**는 것을 직접 겪었다.
> '지금 뜨는 글'을 최근 기준으로 바꾸자 부풀리기가 **오히려 쉬워졌다.**

# 6. 세션이 하나만 있는 게 맞는가 — 나누는 기준

## 두 갈래로 읽힌다

**갈래 A — 한 사람에게 세션이 하나여야 하나**

한 계정 한 세션으로 만들었다가 **되돌렸다.**

```
한 곳만   훔친 세션이 재로그인 한 번에 쫓겨남 · 대신 PC+폰 동시 사용 불가
여러 곳   편한데, 훔친 세션이 '내 기기 중 하나'로 숨음 → 기기 목록이 짝으로 필요
```

→ **"여러 곳 허용 + 기기 목록"**. 네이버·구글이 하는 방식이다.

**갈래 B — 세션 하나에 성격이 다른 값 넷을 담는 게 맞나**

| 값 | 언제 생기나 | 얼마나 자주 바뀌나 | 무슨 일 |
|---|---|---|---|
| `csrf_token` | 폼을 처음 그릴 때 | 거의 안 바뀜 | 위조 요청 차단 |
| `user_id` | 로그인할 때 | 안 바뀜 | 신원 |
| `auth_at` | 로그인·재인증 | 가끔 | sudo 시계 |
| `last_seen` | 로그인 후 | **매 요청** | 유휴 시계 |

**→ 나누지 않는 게 맞다.** 성격은 달라도 **수명이 같다** — 전부 "이 방문" 동안만 살면 된다.

## ★ 신뢰 등급은 이미 동작하고 있다 — 저장하지 않고

우리는 `$_SESSION['trust_level'] = 2` 같은 걸 만든 적이 없다.
**어떤 값이 들어 있느냐가 곧 등급**이다.

```
csrf_token 만              →  글 읽기 · 로그인 폼 제출
+ user_id · last_seen      →  글쓰기 · 댓글 · 추천
+ auth_at (15분 안)        →  영구삭제 · 비번 변경 · 기기 끊기
```

**왜 이게 나은가 — 등급을 저장하면 거짓말할 수 있다.**
`trust_level=2` 인데 `user_id`가 없다면? **모순 상태**가 된다.
값의 존재 자체가 등급이면 **모순이 생길 수 없다.**

**그리고 등급이 저절로 내려간다.** `auth_at`은 시각이라 15분이 지나면
**아무도 아무것도 안 했는데** 권한이 줄어든다 → **강등 코드가 없으니 강등을 빠뜨릴 수도 없다.**

## 그래서 기준 — 언제 나누고 언제 합치나

**나눈다 (다른 그릇으로)**

- **수명이 다를 때** — 세션은 30분, 기기 기록은 계속 살아야 함 → `user_devices` 분리
- **접근 패턴이 다를 때** — 세션은 요청마다, 조회 기록은 가끔 → `post_views` 분리
- **주인이 다를 때** — 이 방문 / 브라우저 / 회원
- **"나중에 증명해야" 할 때** — 판정용과 증빙용은 보관 기간이 반대다
  (`login_attempts` 15분 vs `consent_log` 영구)

**합친다 (한 그릇에)**

- **수명이 같을 때** — 세션의 네 값은 전부 "이 방문" 동안
- **함께 읽고 쓸 때** — 나누면 요청마다 두 곳을 뒤져야 하고 **둘이 어긋날 수 있다**
- **파생 가능할 때** — 등급처럼 다른 값에서 계산되는 것은 **저장하지 않는다**

> ★ **한 문장**: **수명과 주인이 같으면 합치고, 다르면 나눈다.**

## 합치는 대가도 있다 — 실제로 밟았다

> 📂 `auth.php`: *"여기서 갱신하는 건 '마지막으로 움직인 시각'뿐이다.
> **비밀번호 확인 시각(auth_at)까지 같이 갱신하면 sudo 창이 영원히 안 닫힌다.**"*

**한 그릇에 담으면 하나를 만지다 옆을 건드리기 쉽다.**

## 발견한 중복 하나 — 그런데 두는 게 낫다

```
$_SESSION['last_seen']    ← auth.php 가 매 요청 갱신 (유휴 자동 로그아웃용)
sessions.last_active      ← write() 가 매 요청 NOW() 로 갱신 (세션 만료용)
```

**같은 사실을 두 번 적고 있다.** 서로 다른 이유로 각자 생겼고 서로를 몰랐다.

**그래도 합치지 않는다** — `last_active`는 **저장소의 사정**이고 `last_seen`은 **인증 정책**이다.
합치면 `auth.php`가 *"세션이 DB에 있다"* 에 의존하게 되고,
**저장소를 파일로 바꾸면 유휴 타임아웃이 깨진다.**

> **중복이 항상 나쁜 건 아니다.** *"우연히 같은 값"* 과 *"본질적으로 같은 값"* 은 다르다.
