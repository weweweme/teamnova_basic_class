## 1. 실행 방법

```bash
cd lamp
cp .env.example .env      # 윈도우: copy .env.example .env
docker compose up -d
```

**이게 전부다.** 컨테이너가 켜지면서 MariaDB 설치·기동, DB·계정 생성,
`schema.sql`+`seed.sql` 적용, 캐시 폴더 생성까지 `docker/entrypoint.sh`가 자동으로 한다.
진행 상황은 `docker compose logs -f` 의 `[entrypoint]` 줄로 볼 수 있다.

| 항목 | 값 |
|---|---|
| 주소 | `http://localhost:<WEB_PORT>/` — **맥 8080 / 윈도우 8081** (`.env`에서 정함) |
| 웹서버 | Apache (mod_php) · PHP 8.5.8 |
| DB | **MariaDB 12.3.2** (같은 컨테이너, `/usr/local/mariadb`) |
| DocumentRoot | `${APP_DIR}` — docker-compose.yml의 `APP_DIR` 값 (지금은 `/var/www/html/week17`) |
| DB 데이터 | 도커 볼륨 `lamp_mariadb_data` — **컨테이너를 지워도 유지된다** |

**DB 접속 정보** (DBeaver 등 GUI):
| 항목 | 값 |
|---|---|
| Host / Port | `127.0.0.1` / `3306` (`.env`의 `DB_PORT`) |
| Database | `review_community` (utf8mb4) |
| 계정 | `dev` / `dev1234` |

**테스트 계정** (전부 비번 `1234`): `영화광` · `해석러` · `심야극장`

> `.env`는 기기마다 다른 값(이미지 이름·포트)을 담아 Git에 올리지 않는다.
> 이미지(`my_lamp_backup`)는 4GB 바이너리라 Git으로 못 옮긴다 — 각 PC에 있어야 하고,
> 이름이 다르면 `.env`의 `LAMP_IMAGE`를 고친다(`docker images`로 확인).

## 2. DB 세팅 — 자동이지만, 원리는 알아두기

코드는 Git, **데이터는 SQL로 재생성**한다. DB 데이터는 Git으로 옮길 수 없기 때문이다.

```
① sql/schema.sql        — 표 13개 + 외래키 생성        (표가 **아예 없을 때만**)
② sql/migrations/*.sql  — 이미 만들어진 표를 고치는 명령 (001~019 중 아직 안 한 것만, 이름순)
③ sql/seed.sql          — 시연용 데이터 대량            (데이터가 비었을 때만 · 아래 규모)
```

**entrypoint.sh가 ①②③을 알아서 순서대로 실행**하므로 평소엔 신경 쓸 필요가 없다.
어디까지 적용했는지는 `schema_migrations` 표에 파일 이름으로 남는다(게임 패치 노트와 같다).

★ **schema.sql이 옛 모양이어도 괜찮다** — 마이그레이션이 최종 상태까지 데려간다.
실제로 `post_views`는 schema.sql이 만들고 `018`이 지운다. 그래서 최종 표는 **14개**다.
손으로 넣고 싶다면 DBeaver나 CLI로 위 순서대로 실행하면 된다.

**DB를 처음 상태로 되돌리려면** (시연 전 초기화 등):
```bash
docker compose down -v && docker compose up -d
```
`-v`가 DB 볼륨까지 지우므로, 다시 켤 때 schema+seed가 새로 깔린다. **그동안 쌓인 데이터는 사라진다.**

**seed.sql 데이터 규모** (대량 더미 — 시연·발표용):

| 표 | 행 수 | 표 | 행 수 |
|---|---|---|---|
| users | 25 | likes | 1,440 |
| media | **10** | votes | **180** |
| posts | 180 | reports | 36 |
| comments | 367 | notifications | 351 |

**작품별 글 수·추천율을 일부러 벌려 놓았다** — 랭킹·홈 히어로·커뮤니티 그리드가 전부
"글 많은 순"을 쓰는데, 숫자가 비슷하면 정렬이 동작하는지 화면으로 안 보이기 때문이다.

| 작품 | 글 | 추천율 | | 작품 | 글 | 추천율 |
|---|---|---|---|---|---|---|
| 기생충 | 34 | 92% | | 더 글로리 | 15 | 71% |
| 오징어 게임 | 27 | 73% | | 라라랜드 | 13 | 75% |
| 인터스텔라 | 23 | 86% | | 브레이킹 배드 | 12 | 93% |
| 다크 나이트 | 20 | 95% | | 이터널 선샤인 | 10 | 86% |
| 인셉션 | 17 | 79% | | 마스터즈 오브 유니버스 | 9 | **25%** |

마지막 작품은 추천율을 낮게 둬서 **투표 기능이 실제로 반영된다는 걸 한눈에** 보이게 했다.
장르도 영화 7 · 드라마 3으로 섞여 있다.

- seed.sql은 맨 위에서 **싹 비우고(TRUNCATE) 다시 넣으므로 여러 번 실행해도 같은 상태**가 된다.
- 실제 개발 DB를 `mariadb-dump`로 내보내 만든 파일이라 **어느 기기에서 실행해도 동일하게 재현**된다.
- 테스트 계정: `영화광`·`해석러`·`심야극장` + `user1`~`user22` (전부 비번 `1234`).

> ⚠️ `mariadb`/`mysql` CLI로 넣을 땐 한글이 깨지지 않게 `--default-character-set=utf8mb4` 를 붙인다:
> `mariadb -uroot -p --default-character-set=utf8mb4 review_community < sql/seed.sql`

## 3. 표 설계 (ER)

```
users ──┬─< posts >──┬── media
        │     │       │
        ├─< comments >┤
        ├─< likes >───┘ (post)
        └─< votes >──── media
```

| 표 | 내용 | 특징 |
|---|---|---|
| **users** | 회원 | 비밀번호 `password_hash` 저장 · `username`(로그인 신원)과 `nickname`(표시 이름) 분리 |
| **media** | 작품 | TMDB 데이터 (`tmdb_id`·poster·overview) |
| **posts** | 글 | `author_id`→users, `media_id`→media (외래키) |
| **comments** | 댓글 | `post_id`·`author_id` 외래키 |
| **likes** | 글 추천 | **복합키**(user_id, post_id) = 1인 1회 |
| **votes** | 작품 투표 | **복합키**(user_id, media_id) + choice |
| **reports** | 글 신고 | (reporter_id, post_id) UNIQUE = 1인 1회 |
| **notifications** | 알림 | 내 글에 댓글 시 생성 · `is_read`로 안읽음/읽음 |
| **sessions** | 세션 저장소 | ★week16 · PHP 기본값(임시 파일) 대신 여기에 · 세션 ID도 **지문(SHA-256)** 만 |
| **drafts** | 글쓰기 초안 | ★week16 · 세션에 담았다가 옮김 · **복합키**(user_id, work_slug) |
| **consent_log** | 쿠키 동의 증빙 | ★week16 · **append-only**(철회도 새 줄) · users로 가는 FK 없음 · 3년 보관 |
| **login_attempts** | 로그인 시도 | ★week16 · **(아이디+접속지)** 조합으로 센다 · 창(15분)이 지나면 버린다 |
| **user_devices** | 로그인한 기기 | ★week16 · 세션과 **분리**해서 만든다 · 기기 도장(공개키)도 이 줄에 붙는다 |
| **post_view_daily** | 날짜별 조회수 | ★week16 · (글·날짜·**횟수**) — **누가 봤는지가 없다** · 7일 |

> `remember_tokens`(자동 로그인)와 `post_views`(조회 판정)는 **만들었다가 지웠다**
> (마이그레이션 004→009 · 012→018). 왜 되돌렸는지는 그 파일 주석에 그대로 남아 있다 — 11절.

**삭제 정책**: 글을 지우면 그 댓글·추천도 함께(`ON DELETE CASCADE`).
회원은 함부로 못 지우게(`RESTRICT`). 글·댓글 자체는 **소프트삭제**(`deleted_at`)라 되돌리기 가능.

## 4. TMDB 연동 흐름

작품은 우리가 다 저장하지 않는다. **필요할 때만** 우리 DB로 들여온다.

```
[검색]  search.php → TMDB 실시간 검색 (우리 DB 안 거침)
   │ 결과 클릭
[게시판] board/?work=tmdb-496243
   │  → media 표에 있나? 있으면 그 정보 / 없으면 TMDB에서 가져와 표시(폴백)
   │ 글쓰기
[저장]  create.php → ensure_media_by_slug (작품을 media 표에 자동 저장) → posts INSERT
```

- slug 규칙: `tmdb-<tmdb_id>` (예: `tmdb-496243`)
- TMDB 키는 `includes/config.php` (v4 토큰, 헤더 `Authorization: Bearer`)
- 영화(`title`)와 드라마(`name`)의 필드 차이는 `build_media_from_tmdb`가 흡수

**홈·작품목록도 TMDB로** (넷플릭스식):
- 홈 = 히어로 배너 + 사이드바(지금 뜨는 글·오늘의 발견) + 커뮤니티 줄 + TMDB 인기작 줄들 + 최근 글
- 작품목록 = TMDB 인기 영화/드라마 그리드
- `media` 표는 화면 목록이 **아니고**, "글 달린 작품"만 담는 내부 저장소

**캐싱**: `tmdb_get`이 응답을 `cache/tmdb/`에 30분 저장 → 홈 로딩 4.5초 → 0.2초.
(TMDB를 홈 한 번에 10여 회 호출하므로 캐시가 필수. `cache/`는 Git 제외)
- Git은 빈 폴더를 기록하지 않아 새 PC엔 이 폴더가 없다 → **`tmdb_get`이 저장 전에 폴더를 만든다.**
  (예전엔 만들지 않아 캐시가 조용히 실패했고, 매 요청마다 TMDB를 새로 불렀다)

## 5. 코드 구조

### 폴더 규칙 — "자원 하나 = 폴더 하나, 홈만 루트"
```
index.php              홈 (유일한 루트 화면)
works/  search/  rank/  profile/  settings/  notifications/  board/
   └ index.php = 그 자원의 '화면'(GET)   (+ 처리 파일이 있으면 같은 폴더에)
post/   ├ view·write·edit (화면)  └ create·update·delete·restore (처리 POST)
comment/  vote/  like/  report/  auth/    그 자원의 처리(POST) 파일들
profile/avatar.php · settings/{nickname,password,logout_all,revoke_device,confirm,reauth}.php
session/  challenge · enroll · refresh · verify · ping   ★week16 기기 도장 · 활동 신호
consent.php · cookies.php   쿠키 동의(POST 처리) · 쿠키 설정 화면 (★로그인과 무관한 자리)
api/    row.php · browse.php · draft.php   화면(HTML) 대신 데이터(JSON) — 지연 로딩·임시저장
includes/   모든 화면이 공유하는 로직 모듈 + 레이아웃
assets/  sql/  uploads/  cache/   정적파일 · DB재생성 · 업로드물 · TMDB캐시
```
→ **보여주는 URL(뷰)과 처리하는 URL(액션)을 분리**하고, POST 처리 뒤엔 **리다이렉트(PRG)**로
새로고침 중복 제출을 막는다. 자원마다 폴더라 "어느 파일이 어디 있나"가 한 규칙으로 설명된다.

### includes 모듈 — "함수 속만 SQL로"
week14 대비 **화면 파일은 거의 그대로**다. `includes/` 모듈 함수의 내부만 세션→SQL로 바꿨다.

```
includes/
├── config.php     비밀 설정 (TMDB 토큰 · DB 접속정보, Git 제외 대상)
├── session.php    ★week16 세션 켜기 (쿠키 옵션·세션 고정 방어·요청마다 번호표 회전) — util.php가 부른다
├── session_db.php ★week16 세션을 파일 대신 DB 표에 저장 (SessionHandlerInterface 구현)
├── view_session.php ★week16 조회 판정만 담는 **별도 세션**(VIEWSESS) — 쿠키를 하나도 안 쓴다
├── csrf.php       ★week16 위조 요청 방어 (csrf_field / require_csrf)
├── handoff.php    ★week16 알림·가려던 곳·폼 입력값을 쿠키로 나른다 (딱 다음 한 요청만 산다)
├── prefs.php      ★week16 취향 쿠키 (정렬·감상·한 페이지 글 수·최근 검색어·최근 본 글/작품) — 읽을 땐 검증
├── consent.php    ★week16 쿠키 동의 (항목별 선택·방침 버전·consent_log 증빙)
├── devices.php    ★week16 로그인한 기기 목록 (user_devices 표 · device 쿠키)
├── device_key.php ★week16 **기기 도장**(공개키 서명)으로 세션 연장 통제 — DBSC 축소판
├── login_guard.php ★week16 로그인 정문 방어 (시도 제한 · 응답 시간 차이 제거)
├── bot.php        ★week16 봇에게는 세션을 만들지 않는다 (보안 장치가 아니라 청소 장치)
├── drafts.php     ★week16 글쓰기 초안 (drafts 표) — 세션에 담았다가 DB로 옮김
├── db.php         PDO 연결(static 재사용) · db_scalar() 헬퍼
├── tmdb.php       TMDB 호출 (검색·인기작·상세·형식변환) + 30분 캐싱
├── media.php      작품 저장/조회 (ensure_media)
├── auth.php       로그인·회원가입·아바타 · 닉네임/비밀번호 변경 (username≠nickname)
├── posts.php      글 CRUD (조회는 JOIN, 삭제는 소프트삭제)
├── comments.php   댓글 CRUD
├── works.php      작품 조회·투표 (DB+TMDB 폴백) · 커뮤니티 작품
├── ranking.php    랭킹 집계 (유저 랭킹 = users↔posts↔likes JOIN)
├── level.php      유저 등급 배지 (글 수 → 5단계)
├── notifications.php  알림 생성·조회·읽음 처리
├── reports.php    신고 저장 (1인 1회)
├── upload.php     프로필 이미지 업로드 (MIME 검증·파일명 재생성)
├── media_row.php  작품 가로 줄 렌더링 조각 (홈에서 재사용)
└── util.php · header.php · footer.php
```

**핵심 원리:** `get_posts()`가 `posts + media + users`를 **JOIN**해서
week14와 **똑같은 모양의 배열**을 돌려준다 → 그 위의 필터·정렬·페이징·화면이 그대로 재사용됨.

  - 히어로 배너 (커뮤니티 1위 작품의 TMDB backdrop) + 사이드바(🔥지금 뜨는 글·🎲오늘의 발견)

  - 아래: 커뮤니티 5칸 그리드(글 많은 순 상위 5) → TMDB 인기작 가로 줄들 → [최근 글 | 댓글 많은 글] 2단 게시판
- **가로 줄**: 스크롤바 숨김 + JS로 `‹ ›` 화살표 · 마우스휠→가로 스크롤 (`main.js`).
- **폭**: 본문 1400px (홈·게시판·목록), 글 읽기·폼은 760px 유지.
- **반응형**: 미디어 쿼리로 태블릿·모바일에서 포스터·여백·칸 수 축소.

## 7. 안전장치

| 항목 | 방법 |
|---|---|
| SQL 인젝션 | 모든 쿼리 **Prepared Statement** (`?` + `execute([...])`) |
| XSS | 출력은 `e()` = `htmlspecialchars()` |
| 비밀번호 | `password_hash` 저장 · `password_verify` 대조 (평문 없음) |
| 1인 1회 | likes·votes **복합 기본키**로 DB가 구조적으로 보장 |
| 데이터 무결성 | **외래키** — 없는 회원/작품의 글은 DB가 거부 |
| 권한 | 수정·삭제는 화면에서 숨기고 **서버에서 소유권 재확인**(`is_owner`) |
| GET으로 변경 차단 | 액션 파일은 POST 아니면 즉시 리다이렉트 |
| **이미지 업로드** | ①MIME 검사(finfo) ②파일명 강제 재생성 ③업로드 폴더 PHP 실행 차단 |

| **사칭** ✅ | 신원이 **세션**에 있어 사용자가 못 고친다. `?as=`를 아무리 고쳐도 무시된다 |
| 세션 고정 공격 | 로그인·**재인증** 시 `session_regenerate_id(true)` + `use_strict_mode`(`validateId()`를 직접 구현해야 실제로 돈다) |
| 세션 번호표 탈취 | `HttpOnly`(JS가 못 읽음) · `SameSite=Lax` · `Secure`(https) + **요청마다 번호표 회전**(옛것 30초 유예) |
| **훔친 번호표의 수명** ✅ | **기기 도장**(브라우저 밖으로 못 꺼내는 공개키)을 1분마다 확인해야 세션이 밀린다 — 도장 없는 쪽은 아무리 요청해도 못 민다 |
| 로그인 정문 | (아이디+접속지) 시도 제한 + **없는 아이디도 더미 해시와 대조**해 응답 시간을 맞춘다 |
| 민감 작업 | 영구삭제·모든 기기 로그아웃 앞에서 **비밀번호 재확인**(sudo 15분) |
| 도청 | **HTTPS** — http로 들어오면 302로 https로 보낸다 (`Secure`가 모든 쿠키에 저절로 붙는다) |

③은 `apache/httpd.conf`의 `<Directory "${APP_DIR}/uploads">`에 있다
(`php_admin_flag engine off` + 스크립트 확장자 접근 거부).
`uploads/avatars/.htaccess`에도 같은 내용이 있지만 **`AllowOverride None`이라 실제로는 무시된다** —
차단이 실제로 걸리는 곳은 httpd.conf 쪽이다.

| **CSRF** ✅ | 폼마다 추측 불가능한 토큰(`csrf_field()`) + POST 처리마다 대조(`require_csrf()`) |

CSRF는 week15에서 **막으려야 막을 수가 없던** 구멍이다. "이 토큰, 내가 발급한 게 맞나"를
대조하려면 서버가 발급 사실을 어딘가 적어둬야 하는데 적을 곳이 없었다.
세션이 생겨서 비로소 가능해졌다 — 자세한 내용은 `includes/csrf.php`.
(`SameSite=Lax`가 이미 상당 부분을 막지만 브라우저가 지켜주는 방어라, 서버가 직접
확인하는 토큰을 함께 둔다 — 이미지 업로드와 같은 **다층 방어**)

**신원은 세션에 있다** — `$_SESSION['user_id']`. 켜는 곳은 `includes/session.php` 한 곳뿐이고,
모든 페이지가 가장 먼저 부르는 `util.php`가 그 파일을 불러준다.

- 읽는 곳은 `auth.php`의 `current_user_row()` **하나뿐**. 세션엔 회원 **번호만** 담고
  닉네임·아바타는 매 요청 DB에서 읽는다 — 설정에서 바꿨는데 다시 로그인해야 반영되는
  버그를 피하려고. (요청당 DB 조회는 `static` 캐시가 1회로 줄여준다)
- **알림(flash)은 쿠키로 나른다** — `includes/handoff.php`. `take_flash()`가 꺼내면서 지운다.
  → 주소는 이제 **'무엇을 보여줄지'**(작품·검색어·정렬·페이지)만 담는다. 원래 주소가 할 일이다.
  ★ 세션이 아니라 쿠키인 이유: 문구를 고쳐봐야 **자기 화면에 자기가 쓴 글자**가 뜰 뿐이고,
  **쿠키는 남이 못 심는다**(주소는 링크로 뿌릴 수 있어서 위험했던 것이다).
- **'최근 본 글'이 살아났다** — 쿠키에 글 번호 5개(`"3,2,1"`). 홈 사이드바 👀 칸.
  week15가 "주소로는 못 나른다"며 비워뒀던 자리다. 처음엔 세션에 뒀다가 **창을 껐다 켤 때마다
  목록이 비어서** 쿠키로 옮겼다 — 11절 '되돌린 판단'.

## 8. 커뮤니티 기능

- **랭킹** (`rank/`, 상단바): 탭 3종 — 🎬 인기 작품 / 👑 명예의 전당(유저) / 🔥 화제의 글.
  1~3위 메달. 매 요청 DB 집계라 자동 갱신. 유저 랭킹은 **users↔posts↔likes JOIN + GROUP BY**
  (글 수 `COUNT(DISTINCT)`, 받은 추천 `COUNT`) — JOIN으로 줄이 불어나므로 DISTINCT가 필요한 실사례.
- **게시판 상단 작품 상세**: 감독·출연·분량 + ▶ 예고편 모달(유튜브).
  TMDB `append_to_response=credits,videos`로 한 번에 받음 (`build_tmdb_detail`).
- **마이페이지 · 설정 분리**:
  - 공개 프로필(`profile/`)은 아바타·통계·작성 글만. 내 프로필이면 `⚙️ 설정` 링크.
  - 설정(`settings/`, 로그인 전용): 프로필 이미지 · **닉네임 변경** · **비밀번호 변경**
    · **모든 기기에서 로그아웃**(★week16 — 이 기기만 남긴다 · sudo 필요)
    · **로그인한 기기 목록**(★week16 — `user_devices`. 골라서 끊으면 그 기기의 세션·도장이 함께 죽는다).
  - 비밀번호 변경은 **현재 비밀번호 확인 후**에만 (무단 변경 방지).
- **아이디 ↔ 닉네임 분리**: `username`=로그인·소유권·프로필URL(신원, 고정),
  `nickname`=화면 표시 이름(변경 가능). 표시만 닉네임으로 바꾸고 권한 로직은 username 유지.
- **유저 등급 배지** (`includes/level.php`): 작성 글 수로 5단계(🌱새싹→👑시네필).
  글·댓글·프로필·랭킹의 작성자 옆에 배지 표시. 규칙은 한 곳(등급표)에서 관리.
- **좋아요한 글** (프로필 탭): `likes`를 역방향 조회(likes→posts JOIN)해 유저가 추천한 글 모아보기.
- **댓글 알림** (`notifications` 표, 상단바 🔔): 내 글에 남이 댓글 달면 알림 생성(자기 댓글 제외).
  안 읽은 개수 뱃지 → 목록(`notifications/`)을 열면 전체 읽음 처리.
- **휴지통** (설정 안, `trash/`): 삭제한 글은 `deleted_at`을 타임스탬프로 써서 30일 보관.
  되돌리기 / 지금 영구삭제 가능. **cron이 없어** 휴지통을 열 때 만료분을 함께 정리(lazy purge).
  영구삭제 시 댓글·추천·알림도 외래키 CASCADE로 함께 삭제.

## 11. week16에서 물려받은 것 — 쿠키와 세션

> week16의 주제였다. **①~㊼ 전부 완료.** 자세한 경위는 `src/CLAUDE.md`의 week16 절과
> 각 파일 맨 위 주석에 있다. 여기서는 **week17이 딛고 설 결과만** 정리한다.

### 한 문장으로

> **HTTP는 요청 하나하나가 서로를 기억하지 못한다.**
> week15는 그 문제를 **주소로** 풀었고, week16은 **서버(세션)와 브라우저(쿠키)로** 풀었다.

### 그릇을 고르는 세 가지 질문

1. **틀리면 손해 보는가?** — 손해 보면 **세션**, 취향일 뿐이면 **쿠키**
2. **이 값의 주인이 누구인가?** — 브라우저면 **쿠키** / 이 방문이면 **세션** / 회원이면 **DB 표**
3. **지금 동작에 필요한가, 나중에 증명해야 하는가?** — 증명해야 하면 **DB에 append-only**
   (동의 증빙 `consent_log`가 여기서 갈렸다)

그리고 하나 더: **쿠키에서 읽은 값은 주소로 들어온 값과 똑같이 검증한다.**
선택값은 허용 목록 대조 / 숫자는 `ctype_digit`+허용 목록 / slug는 모양(정규식) 검사.

### 지금 무엇이 어디에 있나

| 값 | 어디에 | 왜 |
|---|---|---|
| 로그인 신원 (`user_id`) | 세션 | 틀리면 **남이 된다**(week15의 `?as=` 사칭) |
| CSRF 토큰 | 세션 | 발급 사실을 기억해야 대조할 수 있다 |
| 비번 확인 시각 (`auth_at`) · 마지막 활동 (`last_seen`) | 세션 | **시계를 사용자가 들고 있으면 그건 시계가 아니다** |
| 기기 도장 시계 (`key_proof_at` 외 2개) | 세션 + `user_devices` | 세션에만 두면 **훔친 쪽이 같이 가져간다** |
| 조회 판정 (`seen`) | **별도 세션** `VIEWSESS` | 쿠키면 지우고 부풀린다 · 표면 **열람 이력이 한자리에 모인다** |
| 알림 · 가려던 곳 · 폼 입력값 | 쿠키 (`handoff.php`) | 내가 나를 속이는 건 공격이 아니다 · **쿠키는 남이 못 심는다** |
| 정렬 · 감상 · 한 페이지 글 수 · 최근 검색어 · 최근 본 글/작품 | 쿠키 | 브라우저를 닫아도 남아야 하고, 틀려도 손해가 없다 |
| 기기 번호 (`device`) | 쿠키 | 뜻 없는 무작위 번호 — 내용은 전부 서버에 |
| 글 초안 · 동의 증빙 · 로그인 시도 · 기기 기록 · 날짜별 조회수 | DB 표 | 주인이 **회원**이거나, 나중에 **증명·집계**해야 하는 값 |

- **세션(`PHPSESSID`) 열쇠 7개** — `user_id` · `csrf_token` · `auth_at` · `last_seen` ·
  `key_proof_at` · `key_challenge` · `key_enroll_ok`. **일곱 다 고치면 실제로 이득을 본다.**
- **우리가 심는 쿠키 11개** — `pref_sort` · `pref_sentiment` · `per_page` · `recent_search` ·
  `recent_posts` · `recent_works` · `consent` · `device` + handoff 3개
  (`flash` · `intended` · `old_input` — **만료를 안 주는 유일한 것들** = 창을 닫으면 사라진다)
  (+ PHP가 심는 `PHPSESSID`)
- **DB 표 14개** — week15의 8개 + `sessions` · `drafts` · `consent_log` · `login_attempts` ·
  `user_devices` · `post_view_daily`

### ★ 되돌린 판단 — 이쪽이 더 중요하다

week16에서 **만들었다가 없앤 것이 넷**이다. 지운 이유가 만든 이유보다 길다.

- **자동 로그인(remember)** — 오래 사는 열쇠를 사용자 PC에 맡기는 일이다. 회전·도난 탐지까지
  만들었지만 **완화는 되어도 해결은 안 됐다**(bearer 모델의 성질). → 로그인 상태는 **세션 하나로만**.
- **로그인 기기 목록** — 처음엔 `sessions` 표를 그대로 보여줬다. **세션과 기기를 혼동한 것**이었다
  (세션은 30분이면 죽고, 기기 기록은 로그아웃해도 남아야 한다). → `user_devices`로 **다시 만들었다**.
- **🆕 배지 / `last_visit` 쿠키** — '우리가 알아서 쌓는 기록'을 줄이면서 함께 걷어냈다.
- **조회 판정 표 (`post_views`)** — *"뻥튀기를 막는 기술에서 **블랙리스트를 만드는 기술**로
  넘어갔다"* 는 지적을 받았다. → 판정은 별도 세션으로, 표에는 **누가 봤는지가 없는 숫자만** 남겼다.

그리고 **켜뒀는데 안 돌던 것이 하나** — `use_strict_mode`. 저장소를 DB로 갈아 끼우는 순간
PHP가 판단을 물어볼 곳(`validateId()`)이 사라져 **아무 번호표나 받고 있었다.**
★ **설정을 켜는 것과 그 설정이 도는 것은 다르다.**

## 12. week17 계획 — 프레임워크 적용과 게시판 페이징 ★이번 주차

### 한 문장으로

> week16까지는 **무엇을 어디에 담을지**를 정하는 주차였다.
> week17은 **그 코드를 어떤 모양으로 세울지**를 정하는 주차다.

### ⚠️ 프레임워크는 아직 안 정했다

먼저 충분히 논의한 뒤에 고른다. 지금 확정된 것은 **제약**뿐이다.

| 제약 | 내용 |
|---|---|
| **CLI가 없다** | 컨테이너 안에 `php` CLI도 `composer`도 없다 (`curl`·`unzip`만 있다) |
| 필수 스택 | PHP · MariaDB · Apache(mod_php) — 교수 지정이라 대체 스택은 선택지가 아니다 |
| 환경 개조 비용 | 이미지에 PHP CLI를 새로 설치하는 일은 **되돌리기 어렵다** → 고르기 전에 값을 따진다 |

★ **우리에게 유리한 조건이 하나 있다.** week14→15에서 `includes/` 모듈의 '속만 SQL로' 갈아
끼웠고, week16에서도 세션 저장소(파일→DB)와 초안 저장소(세션→DB)를 바꾸면서 **호출부를 한
글자도 안 고쳤다.** 함수 이름과 반환 모양이 이미 여러 번 버텨 봤다는 뜻이다.
→ 프레임워크를 얹을 때도 **화면·호출부를 안 고치는 쪽**을 먼저 검토한다.

### 게시판 페이징 — 없던 걸 만드는 게 아니다

페이징은 week15부터 이미 돈다.

| 어디 | 한 페이지에 | 파라미터 |
|---|---|---|
| 게시판 글 목록 | 15개 (쿠키로 15/30/50) | `?page=` · `per_page` 쿠키 |
| 글 보기의 댓글 | **원댓글 20개** (답글은 부모를 따라간다) | `?cpage=` |
| 검색 전용 화면 | 20개 | `?page=` |

- **원댓글 기준으로 자르는 이유**: 줄 단위로 자르면 **답글이 부모와 다른 페이지로 찢어진다.**
- **작성·수정·삭제 후에는 그 댓글이 보이는 페이지로** 돌아간다. 알림 링크에도 그 번호가 실린다.
- **목록 파이프라인 순서**: 작품 → 검색 → 감상 필터 → 정렬 → **페이징**
  (다 거른 뒤라야 총 페이지 수를 셀 수 있다)

→ 이번 주차의 일은 화면 파일마다 흩어져 있는 `page`·`perPage`·`totalPages` 계산과
페이지 이동 UI를 **한 자리로 모으는 쪽**에 가깝다. 구체 범위는 논의 후 확정한다.

⚠️ **이미 밟은 함정이 있다** — `$perPage`를 **쓰는 곳보다 뒤에서 정의**해 `DivisionByZeroError`가
났다. **파라미터 처리는 화면 계산보다 반드시 앞에 둔다.**
그리고 `per_page`는 *"숫자니까 안전"* 이 아니라 **"우리가 정한 값인가"** 로 검사한다 —
그대로 썼으면 `?per=100000` 으로 서버를 갈아버릴 수 있다.
