# week16 — 영화·드라마 리뷰 커뮤니티 (MariaDB 연동)

**주제: 쿠키와 세션 적용**

week15를 통째로 복사해서 시작합니다. 기능은 week15와 같고, **"서버가 요청 사이에
무엇을 어떻게 기억하는가"** 를 통째로 바꾸는 주차입니다.

week15는 세션을 **한 개도** 쓰지 않았습니다. 로그인 상태도, 알림도 전부 주소에 실어
날랐습니다(`?as=영화광`). 그 방식을 끝까지 밀어붙였더니 한계가 코드에 흉터로 남았습니다 —
**주소만 고치면 남을 사칭할 수 있고**, 주소는 지저분해졌고, '최근 본 글'은 아예 못 만들었습니다.

week16은 **새 기능을 더하는 주차가 아니라 그 흉터를 걷어내는 주차**입니다.
→ **11절**에 무엇을 왜 바꾸는지 정리해 두었습니다.

> 아래 1~10절은 week15에서 물려받은 현재 상태입니다.
> (DB·TMDB·UI 등은 그대로 두고 '기억하는 방식'만 바꿉니다)

## 1. 실행 방법

```bash
cd lamp
cp .env.example .env      # 윈도우: copy .env.example .env
docker compose up -d
```

**이게 전부다.** 컨테이너가 켜지면서 MariaDB 설치·기동, DB·계정 생성,
`schema.sql`+`seed.sql` 적용, 캐시 폴더 생성까지 `docker/entrypoint.sh`가 자동으로 한다.
진행 상황은 `docker compose logs -f` 의 `[entrypoint]` 줄로 볼 수 있다.

| 항목 | 값 |
|---|---|
| 주소 | `http://localhost:<WEB_PORT>/` — **맥 8080 / 윈도우 8081** (`.env`에서 정함) |
| 웹서버 | Apache (mod_php) · PHP 8.5.8 |
| DB | **MariaDB 12.3.2** (같은 컨테이너, `/usr/local/mariadb`) |
| DocumentRoot | `${APP_DIR}` — docker-compose.yml의 `APP_DIR` 값 (지금은 `/var/www/html/week16`) |
| DB 데이터 | 도커 볼륨 `lamp_mariadb_data` — **컨테이너를 지워도 유지된다** |

**DB 접속 정보** (DBeaver 등 GUI):
| 항목 | 값 |
|---|---|
| Host / Port | `127.0.0.1` / `3306` (`.env`의 `DB_PORT`) |
| Database | `review_community` (utf8mb4) |
| 계정 | `dev` / `dev1234` |

**테스트 계정** (전부 비번 `1234`): `영화광` · `해석러` · `심야극장`

> `.env`는 기기마다 다른 값(이미지 이름·포트)을 담아 Git에 올리지 않는다.
> 이미지(`my_lamp_backup`)는 4GB 바이너리라 Git으로 못 옮긴다 — 각 PC에 있어야 하고,
> 이름이 다르면 `.env`의 `LAMP_IMAGE`를 고친다(`docker images`로 확인).

## 2. DB 세팅 — 자동이지만, 원리는 알아두기

코드는 Git, **데이터는 SQL로 재생성**한다. DB 데이터는 Git으로 옮길 수 없기 때문이다.

```
① sql/schema.sql  — 표 8개 + 외래키 생성
② sql/seed.sql    — 시연용 데이터 대량 (아래 규모)
```

**entrypoint.sh가 "표가 없으면 ①, 데이터가 비었으면 ②"를 알아서 실행**하므로 평소엔 신경 쓸 필요가 없다.
손으로 넣고 싶다면 DBeaver나 CLI로 위 순서대로 실행하면 된다.

**DB를 처음 상태로 되돌리려면** (시연 전 초기화 등):
```bash
docker compose down -v && docker compose up -d
```
`-v`가 DB 볼륨까지 지우므로, 다시 켤 때 schema+seed가 새로 깔린다. **그동안 쌓인 데이터는 사라진다.**

**seed.sql 데이터 규모** (대량 더미 — 시연·발표용):

| 표 | 행 수 | 표 | 행 수 |
|---|---|---|---|
| users | 25 | likes | 1,440 |
| media | **10** | votes | **180** |
| posts | 180 | reports | 36 |
| comments | 367 | notifications | 351 |

**작품별 글 수·추천율을 일부러 벌려 놓았다** — 랭킹·홈 히어로·커뮤니티 그리드가 전부
"글 많은 순"을 쓰는데, 숫자가 비슷하면 정렬이 동작하는지 화면으로 안 보이기 때문이다.

| 작품 | 글 | 추천율 | | 작품 | 글 | 추천율 |
|---|---|---|---|---|---|---|
| 기생충 | 34 | 92% | | 더 글로리 | 15 | 71% |
| 오징어 게임 | 27 | 73% | | 라라랜드 | 13 | 75% |
| 인터스텔라 | 23 | 86% | | 브레이킹 배드 | 12 | 93% |
| 다크 나이트 | 20 | 95% | | 이터널 선샤인 | 10 | 86% |
| 인셉션 | 17 | 79% | | 마스터즈 오브 유니버스 | 9 | **25%** |

마지막 작품은 추천율을 낮게 둬서 **투표 기능이 실제로 반영된다는 걸 한눈에** 보이게 했다.
장르도 영화 7 · 드라마 3으로 섞여 있다.

- seed.sql은 맨 위에서 **싹 비우고(TRUNCATE) 다시 넣으므로 여러 번 실행해도 같은 상태**가 된다.
- 실제 개발 DB를 `mariadb-dump`로 내보내 만든 파일이라 **어느 기기에서 실행해도 동일하게 재현**된다.
- 테스트 계정: `영화광`·`해석러`·`심야극장` + `user1`~`user22` (전부 비번 `1234`).

> ⚠️ `mariadb`/`mysql` CLI로 넣을 땐 한글이 깨지지 않게 `--default-character-set=utf8mb4` 를 붙인다:
> `mariadb -uroot -p --default-character-set=utf8mb4 review_community < sql/seed.sql`

## 3. 표 설계 (ER)

```
users ──┬─< posts >──┬── media
        │     │       │
        ├─< comments >┤
        ├─< likes >───┘ (post)
        └─< votes >──── media
```

| 표 | 내용 | 특징 |
|---|---|---|
| **users** | 회원 | 비밀번호 `password_hash` 저장 · `username`(로그인 신원)과 `nickname`(표시 이름) 분리 |
| **media** | 작품 | TMDB 데이터 (`tmdb_id`·poster·overview) |
| **posts** | 글 | `author_id`→users, `media_id`→media (외래키) |
| **comments** | 댓글 | `post_id`·`author_id` 외래키 |
| **likes** | 글 추천 | **복합키**(user_id, post_id) = 1인 1회 |
| **votes** | 작품 투표 | **복합키**(user_id, media_id) + choice |
| **reports** | 글 신고 | (reporter_id, post_id) UNIQUE = 1인 1회 |
| **notifications** | 알림 | 내 글에 댓글 시 생성 · `is_read`로 안읽음/읽음 |

**삭제 정책**: 글을 지우면 그 댓글·추천도 함께(`ON DELETE CASCADE`).
회원은 함부로 못 지우게(`RESTRICT`). 글·댓글 자체는 **소프트삭제**(`deleted_at`)라 되돌리기 가능.

## 4. TMDB 연동 흐름

작품은 우리가 다 저장하지 않는다. **필요할 때만** 우리 DB로 들여온다.

```
[검색]  search.php → TMDB 실시간 검색 (우리 DB 안 거침)
   │ 결과 클릭
[게시판] board/?work=tmdb-496243
   │  → media 표에 있나? 있으면 그 정보 / 없으면 TMDB에서 가져와 표시(폴백)
   │ 글쓰기
[저장]  create.php → ensure_media_by_slug (작품을 media 표에 자동 저장) → posts INSERT
```

- slug 규칙: `tmdb-<tmdb_id>` (예: `tmdb-496243`)
- TMDB 키는 `includes/config.php` (v4 토큰, 헤더 `Authorization: Bearer`)
- 영화(`title`)와 드라마(`name`)의 필드 차이는 `build_media_from_tmdb`가 흡수

**홈·작품목록도 TMDB로** (넷플릭스식):
- 홈 = 히어로 배너 + 사이드바(지금 뜨는 글·오늘의 발견) + 커뮤니티 줄 + TMDB 인기작 줄들 + 최근 글
- 작품목록 = TMDB 인기 영화/드라마 그리드
- `media` 표는 화면 목록이 **아니고**, "글 달린 작품"만 담는 내부 저장소

**캐싱**: `tmdb_get`이 응답을 `cache/tmdb/`에 30분 저장 → 홈 로딩 4.5초 → 0.2초.
(TMDB를 홈 한 번에 10여 회 호출하므로 캐시가 필수. `cache/`는 Git 제외)
- Git은 빈 폴더를 기록하지 않아 새 PC엔 이 폴더가 없다 → **`tmdb_get`이 저장 전에 폴더를 만든다.**
  (예전엔 만들지 않아 캐시가 조용히 실패했고, 매 요청마다 TMDB를 새로 불렀다)

## 5. 코드 구조

### 폴더 규칙 — "자원 하나 = 폴더 하나, 홈만 루트"
```
index.php              홈 (유일한 루트 화면)
works/  search/  rank/  profile/  settings/  notifications/  board/
   └ index.php = 그 자원의 '화면'(GET)   (+ 처리 파일이 있으면 같은 폴더에)
post/   ├ view·write·edit (화면)  └ create·update·delete·restore (처리 POST)
comment/  vote/  like/  report/  auth/    그 자원의 처리(POST) 파일들
profile/avatar.php · settings/{nickname,password}.php   내 정보 편집 처리
api/    row.php · browse.php   화면(HTML) 대신 데이터(JSON) — 지연 로딩용
includes/   모든 화면이 공유하는 로직 모듈 + 레이아웃
assets/  sql/  uploads/  cache/   정적파일 · DB재생성 · 업로드물 · TMDB캐시
```
→ **보여주는 URL(뷰)과 처리하는 URL(액션)을 분리**하고, POST 처리 뒤엔 **리다이렉트(PRG)**로
새로고침 중복 제출을 막는다. 자원마다 폴더라 "어느 파일이 어디 있나"가 한 규칙으로 설명된다.

### includes 모듈 — "함수 속만 SQL로"
week14 대비 **화면 파일은 거의 그대로**다. `includes/` 모듈 함수의 내부만 세션→SQL로 바꿨다.

```
includes/
├── config.php     비밀 설정 (TMDB 토큰 · DB 접속정보, Git 제외 대상)
├── session.php    ★week16 세션 켜기 (쿠키 옵션·세션 고정 방어) — util.php가 부른다
├── csrf.php       ★week16 위조 요청 방어 (csrf_field / require_csrf)
├── db.php         PDO 연결(static 재사용) · db_scalar() 헬퍼
├── tmdb.php       TMDB 호출 (검색·인기작·상세·형식변환) + 30분 캐싱
├── media.php      작품 저장/조회 (ensure_media)
├── auth.php       로그인·회원가입·아바타 · 닉네임/비밀번호 변경 (username≠nickname)
├── posts.php      글 CRUD (조회는 JOIN, 삭제는 소프트삭제)
├── comments.php   댓글 CRUD
├── works.php      작품 조회·투표 (DB+TMDB 폴백) · 커뮤니티 작품
├── ranking.php    랭킹 집계 (유저 랭킹 = users↔posts↔likes JOIN)
├── level.php      유저 등급 배지 (글 수 → 5단계)
├── notifications.php  알림 생성·조회·읽음 처리
├── reports.php    신고 저장 (1인 1회)
├── upload.php     프로필 이미지 업로드 (MIME 검증·파일명 재생성)
├── media_row.php  작품 가로 줄 렌더링 조각 (홈에서 재사용)
└── util.php · header.php · footer.php
```

**핵심 원리:** `get_posts()`가 `posts + media + users`를 **JOIN**해서
week14와 **똑같은 모양의 배열**을 돌려준다 → 그 위의 필터·정렬·페이징·화면이 그대로 재사용됨.

## 7. 안전장치

| 항목 | 방법 |
|---|---|
| SQL 인젝션 | 모든 쿼리 **Prepared Statement** (`?` + `execute([...])`) |
| XSS | 출력은 `e()` = `htmlspecialchars()` |
| 비밀번호 | `password_hash` 저장 · `password_verify` 대조 (평문 없음) |
| 1인 1회 | likes·votes **복합 기본키**로 DB가 구조적으로 보장 |
| 데이터 무결성 | **외래키** — 없는 회원/작품의 글은 DB가 거부 |
| 권한 | 수정·삭제는 화면에서 숨기고 **서버에서 소유권 재확인**(`is_owner`) |
| GET으로 변경 차단 | 액션 파일은 POST 아니면 즉시 리다이렉트 |
| **이미지 업로드** | ①MIME 검사(finfo) ②파일명 강제 재생성 ③업로드 폴더 PHP 실행 차단 |

| **사칭** ✅ | 신원이 **세션**에 있어 사용자가 못 고친다. `?as=`를 아무리 고쳐도 무시된다 |
| 세션 고정 공격 | 로그인 시 `session_regenerate_id(true)` + `session.use_strict_mode` |
| 세션 번호표 탈취 | 세션 쿠키에 `HttpOnly`(JS가 못 읽음) · `SameSite=Lax` |

③은 `apache/httpd.conf`의 `<Directory "${APP_DIR}/uploads">`에 있다
(`php_admin_flag engine off` + 스크립트 확장자 접근 거부).
`uploads/avatars/.htaccess`에도 같은 내용이 있지만 **`AllowOverride None`이라 실제로는 무시된다** —
차단이 실제로 걸리는 곳은 httpd.conf 쪽이다.

| **CSRF** ✅ | 폼마다 추측 불가능한 토큰(`csrf_field()`) + POST 처리마다 대조(`require_csrf()`) |

CSRF는 week15에서 **막으려야 막을 수가 없던** 구멍이다. "이 토큰, 내가 발급한 게 맞나"를
대조하려면 서버가 발급 사실을 어딘가 적어둬야 하는데 적을 곳이 없었다.
세션이 생겨서 비로소 가능해졌다 — 자세한 내용은 `includes/csrf.php`.
(`SameSite=Lax`가 이미 상당 부분을 막지만 브라우저가 지켜주는 방어라, 서버가 직접
확인하는 토큰을 함께 둔다 — 이미지 업로드와 같은 **다층 방어**)

**신원은 세션에 있다** — `$_SESSION['user_id']`. 켜는 곳은 `includes/session.php` 한 곳뿐이고,
모든 페이지가 가장 먼저 부르는 `util.php`가 그 파일을 불러준다.

- 읽는 곳은 `auth.php`의 `current_user_row()` **하나뿐**. 세션엔 회원 **번호만** 담고
  닉네임·아바타는 매 요청 DB에서 읽는다 — 설정에서 바꿨는데 다시 로그인해야 반영되는
  버그를 피하려고. (요청당 DB 조회는 `static` 캐시가 1회로 줄여준다)
- **알림(flash)도 세션에 있다** — `$_SESSION['flash']`. `take_flash()`가 꺼내면서 지운다.
  → 주소는 이제 **'무엇을 보여줄지'**(작품·검색어·정렬·페이지)만 담는다. 원래 주소가 할 일이다.
- **'최근 본 글'이 살아났다** — 세션에 글 번호 5개. 홈 사이드바 👀 칸.
  week15가 "주소로는 못 나른다"며 비워뒀던 자리다 (11절 ④).

## 8. 커뮤니티 기능

- **랭킹** (`rank/`, 상단바): 탭 3종 — 🎬 인기 작품 / 👑 명예의 전당(유저) / 🔥 화제의 글.

  (글 수 `COUNT(DISTINCT)`, 받은 추천 `COUNT`) — JOIN으로 줄이 불어나므로 DISTINCT가 필요한 실사례.
- **게시판 상단 작품 상세**: 감독·출연·분량 + ▶ 예고편 모달(유튜브).

- **마이페이지 · 설정 분리**:
  - 공개 프로필(`profile/`)은 아바타·통계·작성 글만. 내 프로필이면 `⚙️ 설정` 링크.

- **아이디 ↔ 닉네임 분리**: `username`=로그인·소유권·프로필URL(신원, 고정),
  `nickname`=화면 표시 이름(변경 가능). 표시만 닉네임으로 바꾸고 권한 로직은 username 유지.
- **유저 등급 배지** (`includes/level.php`): 작성 글 수로 5단계(🌱새싹→👑시네필).
  글·댓글·프로필·랭킹의 작성자 옆에 배지 표시. 규칙은 한 곳(등급표)에서 관리.
- **좋아요한 글** (프로필 탭): `likes`를 역방향 조회(likes→posts JOIN)해 유저가 추천한 글 모아보기.
- **댓글 알림** (`notifications` 표, 상단바 🔔): 내 글에 남이 댓글 달면 알림 생성(자기 댓글 제외).
  안 읽은 개수 뱃지 → 목록(`notifications/`)을 열면 전체 읽음 처리.
- **휴지통** (설정 안, `trash/`): 삭제한 글은 `deleted_at`을 타임스탬프로 써서 30일 보관.
  되돌리기 / 지금 영구삭제 가능. **cron이 없어** 휴지통을 열 때 만료분을 함께 정리(lazy purge).
  영구삭제 시 댓글·추천·알림도 외래키 CASCADE로 함께 삭제.

## 11. week16 계획 — 쿠키와 세션 ★이번 주차

### 한 문장으로

> **HTTP는 요청 하나하나가 서로를 기억하지 못한다.**
> week15는 그 문제를 **주소로** 풀었다. week16은 **서버(세션)와 브라우저(쿠키)로** 푼다.

PHP 스크립트는 요청 한 번을 처리하고 **죽는다**. 변수도 함께 사라진다.
그래서 "방금 왔던 그 사람"을 알아보려면 **어딘가에 적어둬야** 한다. 적어둘 곳이 세 군데다 —
주소(week15) · 서버(세션) · 브라우저(쿠키). 이번 주차는 뒤의 둘을 쓴다.

### 세션 vs 쿠키 — 표 하나로

| | **세션** | **쿠키** |
|---|---|---|
| 값이 실제로 있는 곳 | **서버** | **사용자 PC** |
| 브라우저가 들고 다니는 것 | 번호표만 (`PHPSESSID`) | 값 그 자체 |
| 사용자가 고칠 수 있나 | ❌ 못 고친다 | ⭕ 마음대로 고친다 |
| 브라우저를 닫으면 | 사라진다 | 만료일까지 남는다 |
| 그래서 담을 것 | **틀리면 손해 보는 것** | **틀려도 취향일 뿐인 것** |

> **비유**: 세션은 **클럽 물품보관소** — 짐은 카운터 안에 있고 나는 번호표만 들고 다닌다.
> 번호표를 위조해도 남의 짐은 안 나온다. 쿠키는 **내 주머니 속 메모지** — 내용을 내가 직접
> 고쳐 쓸 수 있다. 그래서 "이 사람은 관리자"라고 쿠키에 적으면 안 된다.

★ **세션도 결국 쿠키 위에 올라탄다.** 번호표(`PHPSESSID`)를 쿠키로 주고받기 때문이다.
그러니 "세션이냐 쿠키냐"가 아니라 **"값을 어디에 두느냐"** 의 차이다.

### 세션으로 옮길 것 — "틀리면 손해 보는 것"

#### ① 로그인 상태 (필수 · 이 주차의 본체) — ✅ **완료**

| | 지금 (week15) | week16 |
|---|---|---|

  (공격자가 자기 번호표를 미리 쥐여주고, 피해자가 그걸로 로그인하면 같은 번호표를
  공격자도 갖고 있게 되는 공격. 로그인하는 순간 번호표를 새로 발급하면 무력화된다)

  - `main.js`의 `withIdentity()` (JS가 만든 링크에 손으로 신원 붙이던 것)
- **추가된 것**: `includes/session.php` 1개 파일 + `auth.php`의 `find_user_by_id()`.
  로그아웃은 이제 진짜로 지운다 — ①금고 비우기 ②번호표 쿠키 회수 ③`session_destroy()`.
- **확인한 동작** (`curl`):

  |---|---|
  | 세션 쿠키 옵션 | `PHPSESSID=…; path=/; HttpOnly; SameSite=Lax` ✅ |

#### ② 플래시 메시지 — ✅ **완료**

week15는 `?flash=…&ftype=…&fundo=…&fid=…` **파라미터 4개**를 주소로 날랐다.
그 탓에 문제 셋이 생겼고, 둘은 **우회책을 따로 만들어** 막아야 했다.

| 문제 | week15의 대책 | week16 |
|---|---|---|
| 주소가 지저분해진다 | 대책 없음 (이 방식의 대가) | 주소에 아무것도 안 붙는다 |
| 새로고침하면 또 뜬다 | JS가 `replaceState`로 주소창 청소 | 읽는 순간 지워진다 |
| 알림이 링크를 타고 따라다닌다 | `query_url()`에서 `FLASH_KEYS` 제외 | 링크에 실릴 수가 없다 |

→ 세션에 넣고 **읽으면서 뗀다**(read-once). `take_flash()`의 이름이 그제야 뜻대로 동작한다.

- **지워진 것**: `FLASH_KEYS` · `flash_pending()` · `flash_params()`,
  `redirect()`의 알림 싣기, `query_url()`의 걸러내기, `main.js`의 주소 청소 블록
  (+ `main.js`에 중복으로 두고 양쪽을 같이 고쳐야 했던 `FLASH_URL_KEYS` 목록).
- **호출부 30여 곳은 한 글자도 안 바뀌었다** — `set_flash()` 다음 줄에 `redirect()`.
  알림을 어떻게 나르는지는 원래 그 두 함수 안에만 있던 사정이기 때문이다.
- `UNDO_TARGETS`(되돌리기 버튼 표)는 남겼다. week15에선 `?fundo=`가 주소로 들어와
  **보안 장치**이기도 했지만, 이제는 값을 우리 코드가 넣으므로 단순한 설정 표가 됐다.
  `"12,34"`를 쪼개 배열로 되돌리던 처리도 함께 사라졌다 — 세션은 배열을 배열로 보관한다.
- **확인한 동작**: 로그인 후 리다이렉트 주소 `/` (알림 파라미터 0개) ✅ /
  다음 화면에 알림 1회 표시 ✅ / 새로고침하면 사라짐 ✅ /
  글 삭제 → **되돌리기 버튼**(`action=/post/restore.php`, `id=184`) 정상 → 복구 확인 ✅ /
  전체 화면 11곳 200 ✅ / 링크 속 `flash`·`as` 파라미터 **0건** ✅

#### ③ CSRF 토큰 (새 보안 — 세션이 있어야 비로소 가능) — ✅ **완료**

남의 사이트가 우리 폼을 흉내 내 POST를 쏘는 공격. 이미 로그인된 나를 **시켜먹는** 것이라
비밀번호를 아무리 길게 해도 막히지 않는다. 막으려면 서버가 "이 토큰, 내가 발급한 게 맞나"를
대조해야 하는데 — **week15는 발급한 사실을 적어둘 곳이 없어 시작조차 못 했다.**

- 새 파일 `includes/csrf.php` — 함수 **세 개**뿐이다.
  `csrf_token()`(세션당 하나 발급) · `csrf_field()`(폼에 심을 hidden) · `require_csrf()`(대조).
  `util.php`가 불러주므로 어느 화면·액션에서도 바로 쓸 수 있다.
- 토큰은 `random_bytes(32)` → 16진수 64글자. **`rand()`를 쓰면 안 된다** — 재현 가능한
  난수라 값 몇 개를 보면 다음이 계산된다. 토큰은 추측 불가가 생명이다.
- 대조는 `===`가 아니라 **`hash_equals()`**. `===`는 다른 글자를 만나는 순간 멈춰서
  "몇 글자까지 맞았는지"가 시간 차이로 새어 나간다(타이밍 공격). 이 함수는 항상 끝까지 비교한다.
- **세션당 토큰 하나**를 계속 쓴다. 폼마다 새로 발급하면 탭을 여러 개 열었을 때
  먼저 연 탭의 토큰이 무효가 돼 멀쩡한 제출이 거부된다.
- **적용 범위**: POST 액션 파일 **17개** 전부 + POST 폼 **20개** 전부.
- **확인한 동작**:

  | 시도 | 결과 |
  |---|---|
  | 토큰 없이 로그인 | `⚠️ 잘못된 요청입니다` · 로그인 안 됨 ✅ |
  | 정상 토큰으로 로그인 | `👋 user1님, 환영합니다!` ✅ |
  | 위조 토큰으로 글 삭제 | 거부 · **1번 글 그대로 살아있음** ✅ |
  | 정상 토큰으로 전 기능 | 글·댓글 CRUD, 추천, 투표, 신고, 휴지통, 닉네임 변경 전부 정상 ✅ |
  | 모든 화면의 POST 폼 | 토큰 누락 **0건** ✅ |

> ⚠️ **작업 중 밟은 함정**: `csrf.php` 주석에 사용 예를 적으면서 `?` `>` 를 그대로 썼더니
> **PHP가 거기서 태그를 닫아버려** 파일 아래쪽이 통째로 화면에 글자로 쏟아졌다.
> `//` 한 줄 주석 안에서도 태그 닫기 기호는 살아 있다. 지금은 주석에서 뺐다.

#### ④ '최근 본 글' 부활 — ✅ **완료**

week15가 **못 만들어서 비워둔** 자리. `?recent=1,5,9,…`는 볼수록 길어져 주소로는 나를 수 없었다.
'한 번 쓰고 버리는 값'(신원·알림)은 주소로도 되지만, **쌓이는 값**은 안 된다.

- 함수 이름은 week15 주석이 예고한 그대로 — `remember_recent_post()` / `get_recent_posts()`
  (`includes/posts.php`). 세션에 **글 번호만** 최대 `RECENT_POSTS_MAX`(5)개.
- 기록하는 곳은 `post/view.php`, 보여주는 곳은 홈 사이드바 **👀 최근 본 글**.
- **왜 DB 표가 아닌가**: 표를 파면 기록의 주인이 '브라우저'에서 '회원'으로 바뀐다.
  → 로그인 안 한 방문자는 아예 기록되지 않아 **다른 기능**이 되어버린다.
- **"GET 화면에서 세션에 써도 되나?"** — 된다. GET의 '안전(safe)' 규칙은
  *남들이 보는 자료를 바꾸지 말라*는 뜻이고, 여기서 남기는 건 내 열람 기록뿐이다.
  (쇼핑몰 '최근 본 상품'·조회수 집계도 같은 이유로 GET에서 처리한다)
- 지워진 글은 `get_post()`가 `null`을 주므로 **자동으로 빠진다** — 세션을 따로 청소하지 않는다.
- **확인한 동작**:

  | 확인 | 결과 |
  |---|---|
  | 아무것도 안 본 상태 | 칸 자체를 안 그림 ✅ |
  | 1 → 5 → 9번 열람 | 최신순 `9, 5, 1` ✅ |
  | 1번 다시 열람 | 맨 앞으로 이동(중복 안 쌓임) ✅ |
  | 6개 열람 | 최신 **5개만** 유지 ✅ |
  | 목록의 글을 삭제 | 그 줄만 조용히 빠짐 ✅ |
  | **로그인 안 한 상태** | **정상 동작** ✅ ← DB 표였다면 불가능했을 지점 |

#### ⑤ 조회수 중복 방지 — ✅ **완료**

week15까지 **`posts.views`는 한 번도 안 움직였다.** seed 숫자가 굳어 있었고,
게시판의 `조회` 정렬 탭은 사실상 장식이었다. 이제 진짜로 센다.

- `count_post_view()`(`includes/posts.php`): 세션의 "이번에 본 글" 목록에 없으면 `+1`.
- **왜 쿠키가 아니라 세션인가** — 이 주차의 판단 기준이 그대로 나오는 자리다.
  쿠키에 두면 값이 사용자 PC에 있으니 **지우고 새로고침을 반복해 얼마든지 부풀릴 수 있다.**
  조회수는 랭킹·정렬에 쓰이는 **틀리면 손해 보는 값** → 서버가 들고 있어야 한다.
  (반대로 '게시판 정렬 기본값'은 틀려도 취향일 뿐이라 ⑦에서 쿠키로 간다)
- **`views = views + 1`을 DB가 계산하게 맡긴다.** PHP로 "읽어서 +1 해서 쓰기"를 하면
  두 사람이 동시에 열었을 때 둘 다 320을 읽고 둘 다 321을 써서 한 번이 사라진다(경쟁 상태).
- 글 보기 화면에 **👁 조회수 표시를 새로 달았다** — week15엔 적을 값이 없어 아예 없던 자리다.
  방금 올린 1은 PHP에서 더해 보여준다(그것 하나 때문에 글을 다시 읽는 건 낭비).
- **한계는 솔직하게**: 세션이 사는 동안만 기억하므로 브라우저를 새로 켜면 한 번 더 세어진다.
  '새로고침 연타'라는 제일 흔한 부풀리기는 막지만 완벽하진 않다.
  완전히 막으려면 회원별로 DB에 남겨야 하는데, 그러면 비회원 조회가 안 세어진다.
- **확인한 동작**:

  | 확인 | 결과 |
  |---|---|
  | 같은 세션으로 5번 열기 | `320 → 321` (**+1만**) ✅ |
  | 서로 다른 세션 3개 | `322 → 325` (+3) ✅ |
  | 화면 숫자 | 첫 열람에 **즉시** `👁 321` (새로고침 불필요) ✅ |
  | 재열람 | 화면·DB 모두 `321` 유지 ✅ |

### 쿠키로 옮길 것 — "틀려도 취향일 뿐인 것"

#### ⑥ 자동 로그인 (Remember me)

세션의 한계는 명확하다 — **브라우저를 닫으면 사라진다.** 로그인 폼에 체크박스를 달아 보완한다.

| | |
|---|---|
| ❌ **나쁜 방식** | 쿠키에 아이디·비밀번호를 담는다 → `?as=`와 **똑같은 실수**. 쿠키는 사용자가 고친다 |
| ⭕ **실무 방식** | `random_bytes()`로 **추측 불가능한 토큰**을 만들어 → **쿠키엔 토큰, DB엔 그 해시** |

- 접속 시 토큰을 대조해 통과하면 세션을 복구하고, **토큰을 새것으로 교체**(rotation)한다.
  훔친 토큰이 오래 살아남지 못하게.
- 쿠키 옵션: `HttpOnly`(JS가 못 읽음 → XSS로 훔쳐가는 걸 막음) ·
  `SameSite=Lax`(다른 사이트에서 온 요청엔 안 실림 → CSRF 완화) · 만료 30일.
  `Secure`는 https 전용이라 localhost 개발에선 끄되, **왜 껐는지 주석에 남긴다.**
- **새 표 `remember_tokens`** (user_id · token_hash · expires_at) → 마이그레이션 **`004_`**.
- 로그아웃하면 세션 파기 + 이 쿠키와 DB 토큰까지 함께 삭제한다.

#### ⑦ 취향 쿠키

- **게시판 정렬 기본값** — 마지막에 고른 탭(최신/인기/조회/댓글)을 기억한다.
- **최근 검색어** — 상단바 검색칸에 최근 5개. (틀려도 사용자가 다시 치면 그만)

### 일부러 **하지 않을** 것

- **데이터를 세션에 담기** — week14가 하던 방식이다. 데이터의 정답은 DB이고,
  세션은 "지금 누구인가 · 어디까지 봤나"만 담는다. 되돌아가지 않는다.
- **세션에 회원 정보를 통째로 넣기** — `user_id` **하나만** 넣고 나머지는 매 요청 DB 조회.
  닉네임·아바타를 바꿨는데 **다시 로그인해야 반영되는** 버그가 생기기 때문이다.
  (조회는 `current_user_row()`의 `static` 캐시가 이미 요청당 1회로 줄여준다)

### 진행 순서

**① → ② → ③ → ④ → ⑤ → ⑥ → ⑦.** 앞의 것이 뒤의 것의 토대다 —
세션이 없으면 CSRF 토큰도, 최근 본 글도, 자동 로그인도 시작할 수 없다.

> **시연 포인트**: 먼저 week15에서 주소창의 `as=`를 남의 아이디로 고쳐 **사칭을 성공시켜 보이고**,
> week16에서 같은 짓이 안 통하는 걸 보여준다. 그 다음 **지워진 코드**(URL 리라이터·플래시
> 우회책)를 나란히 놓는다 — "기능이 늘어난 게 아니라 **군더더기가 사라졌습니다**."
