# 발표 원고 — Laravel 의 동작 방식과 코드 변화

레거시 vs 리팩토링 비교(① 규모 ~ ④ 화면) **앞에** 들어가는 부분이다.
코드는 모두 실제 파일에서 옮겼다. 레거시 코드는 이관 직전 커밋 `d92bc54^` 기준이다.

---

## 슬라이드 A. 요청 처리 흐름

- **레거시 — URL 하나에 PHP 파일 하나가 대응한다**
  - `/post/update.php` 요청은 그 파일 하나가 처리 전 과정을 담당한다
    - 파일 불러오기 → 로그인 확인 → CSRF 토큰 확인 → 입력값 검사 → 작성자 확인 → DB 저장 → 리다이렉트
  - 그 결과 파일마다 앞부분에 **같은 확인 코드가 반복된다**
- **Laravel — 모든 요청이 하나의 진입점을 거친다**
  - ① `public/index.php` — 모든 요청의 진입점
  - ② **미들웨어** — 컨트롤러에 도달하기 전에 실행되는 공통 처리 (세션, CSRF 토큰 확인, 로그인 확인)
  - ③ **라우트** — URL 과 처리 메서드의 연결을 정의한 목록 (`routes/web.php`)
  - ④ **컨트롤러** — 해당 기능의 처리만 담은 메서드
  - ⑤ **모델**이 DB 를 조회·저장하고, **Blade** 가 화면을 생성한다
  - ⑥ 응답은 **미들웨어를 역순으로 통과**한 뒤 브라우저로 전송된다
- **익숙한 도구와의 대응**
  - 라우트 ↔ Android 의 `AndroidManifest.xml` — 앱을 구성하는 요소를 한 파일에 등록한다
  - 미들웨어 ↔ Unity 의 `Rigidbody` 컴포넌트 — 컴포넌트를 추가하면 물리 연산 코드를 작성하지 않아도 적용되듯, 라우트에 `auth` 를 지정하면 로그인 확인 코드를 작성하지 않아도 적용된다

> 출처 — [Laravel 13.x · Request Lifecycle](https://laravel.com/docs/13.x/lifecycle)
> - "The entry point for all requests to a Laravel application is the `public/index.php` file."
> - "The HTTP kernel is also responsible for passing the request through the application's middleware stack. These middleware handle reading and writing the HTTP session, determining if the application is in maintenance mode, verifying the CSRF token, and more."
> - "If the request passes through all of the matched route's assigned middleware, the route or controller method will be executed and the response returned by the route or controller method will be sent back through the route's chain of middleware."

## 슬라이드 B. 동일 기능의 전체 코드 비교 — 글 수정

- **레거시 — `post/update.php` 34줄 + `update_post()` 6줄**

```php
require_once __DIR__ . '/../includes/util.php';
require_once __DIR__ . '/../includes/auth.php';
require_once __DIR__ . '/../includes/posts.php';
require_login();
if ($_SERVER['REQUEST_METHOD'] !== 'POST') {
    redirect('/');
}
require_csrf();
$id        = post_int('id', 0);
$title     = trim(post_str('title'));
$content   = trim(post_str('content'));
$sentiment = post_str('sentiment', '보통');
if (!in_array($sentiment, ['호평', '보통', '혹평'], true)) {
    $sentiment = '보통';
}
$target = get_post($id);
if ($id <= 0 || $target === null) {
    redirect('/');
}
if (!is_owner($target['author'])) {
    set_flash('본인이 쓴 글만 수정·삭제할 수 있습니다.', 'error');
    redirect('/post/view.php', ['id' => $id]);
}
if ($title === '' || $content === '') {
    redirect('/post/edit.php', ['id' => $id]);
}
if (mb_strlen($title) > POST_TITLE_MAX || mb_strlen($content) > POST_CONTENT_MAX) {
    set_flash('제목 또는 내용이 너무 깁니다. 줄여서 다시 시도해 주세요.', 'error');
    redirect('/post/edit.php', ['id' => $id]);
}
update_post($id, $title, $content, $sentiment);
set_flash('✏️ 글이 수정되었습니다.');
redirect('/post/view.php', ['id' => $id]);
```

- **Laravel — 라우트 1줄 + `update()` 12줄 + 정책 4줄**

```php
// routes/web.php — 로그인 확인은 라우트에서 지정한다
Route::put('/posts/{post}', [PostController::class, 'update'])->middleware('auth');

// PostController — 이 기능의 처리만 남는다
public function update(Request $request, Post $post)
{
    $this->authorize('update', $post);            // 작성자 확인

    $data = $request->validate([                   // 입력값 검사
        'media_id'  => ['required', 'integer', 'exists:media,id'],
        'title'     => ['required', 'string', 'max:100'],
        'content'   => ['required', 'string', 'max:5000'],
        'sentiment' => ['required', 'in:호평,보통,혹평'],
    ]);

    $post->update($data);                          // 저장 (수정 시각 포함)

    return redirect("/posts/{$post->id}")->with('status', '글을 수정했습니다.');
}

// PostPolicy — 작성자 판단 기준은 이 파일에만 있다
public function update(User $user, Post $post): bool
{
    return $user->id === $post->author_id;
}
```

- **레거시 코드의 각 부분이 대체된 위치**
  - `require_once` 3줄 → 삭제 (Composer 오토로드)
  - `require_login()` · POST 확인 · `require_csrf()` → 라우트 정의와 기본 미들웨어
  - 입력값 추출 · 존재하지 않는 글 확인 → 매개변수 `Post $post` (라우트 모델 바인딩)
  - 작성자 확인 → `authorize()` 호출 1줄 (판단 기준은 정책 파일)
  - 빈 값 · 길이 검사와 리다이렉트 → `validate()` 규칙 배열
  - `UPDATE … edited_at = NOW()` → `$post->update()`

## 슬라이드 C. 프레임워크가 대신하는 요청 검사

### 1) 로그인 확인 — 26곳 → 0곳

- **레거시** — 로그인이 필요한 파일마다 첫 부분에 호출

```php
require_login();
```

- **Laravel** — 라우트 정의에 지정

```php
Route::put('/posts/{post}', [PostController::class, 'update'])->middleware('auth');
```

- 파일별 호출을 하나라도 누락하면 보호되지 않던 구조에서, **라우트 정의만 보고 보호 대상을 확인할 수 있는** 구조로 바뀌었다

> 출처 — [Laravel 13.x · Request Lifecycle](https://laravel.com/docs/13.x/lifecycle#routing)
> "Laravel includes a middleware that verifies if the user of your application is authenticated. If the user is not authenticated, the middleware will redirect the user to the login screen."

### 2) CSRF 토큰 확인 — 25곳 → 0곳

- **레거시** — 처리 파일에서 `require_csrf();` 호출, 폼에 `<?= csrf_field() ?>` 출력
- **Laravel** — 폼에 `@csrf` 만 작성한다. 토큰 확인은 기본 미들웨어가 모든 POST 요청에 수행한다

> 출처 — 슬라이드 A 의 Request Lifecycle 인용 ("verifying the CSRF token")

### 3) 작성자 확인 — 판단 기준을 한 곳으로

- **레거시** — 수정 · 삭제 · 복구 · 영구삭제 파일마다 `if (!is_owner(...)) { set_flash(...); redirect(...); }`
- **Laravel** — `PostPolicy` 에 기준을 한 번 정의하고, 사용하는 곳에서는 한 줄로 호출한다
  - 처리 — `$this->authorize('update', $post);` (권한이 없으면 403 응답)
  - 화면 — `@can('update', $post)` … `@endcan` (수정 버튼 표시 여부)
  - **처리와 화면이 같은 기준을 참조**하므로, 버튼 표시 조건과 실제 허용 조건이 어긋나지 않는다

> 출처 — [Laravel 13.x · Authorization](https://laravel.com/docs/13.x/authorization)
> - "Policies are classes that organize authorization logic around a particular model or resource."
> - "If the action is not authorized, the `authorize` method will throw an `Illuminate\Auth\Access\AuthorizationException` exception which the Laravel exception handler will automatically convert to an HTTP response with a 403 status code"

### 4) 입력값 검사 — 조건문 → 규칙 배열

- **레거시** — 조건마다 `if` 작성 → 오류 메시지 저장 → 입력값 보관 → 폼으로 리다이렉트
- **Laravel** — 규칙만 선언한다

```php
$request->validate(['title' => ['required', 'string', 'max:100']]);
```

```blade
<input name="title" value="{{ old('title') }}">
@error('title') {{ $message }} @enderror
```

> 출처 — [Laravel 13.x · Validation](https://laravel.com/docs/13.x/validation#quick-displaying-the-validation-errors)
> "Laravel will automatically redirect the user back to their previous location. In addition, all of the validation errors and request input will automatically be flashed to the session."

## 슬라이드 D. 프레임워크가 대신하는 반복 코드

### 5) 출력 이스케이프 — `e()` 243곳 → 4곳

- **레거시**

```php
<span class="tag"><?= e($post['sentiment']) ?></span>
<a href="/board/?work=<?= e($post['work']) ?>"><?= e($post['workTitle']) ?></a>
```

- **Laravel**

```blade
<span class="tag">{{ $post->sentiment }}</span>
<a href="/works/{{ $post->media->slug }}">{{ $post->media->title }}</a>
```

- 레거시에서는 `e()` 호출을 누락한 자리가 XSS 취약점이 되었다. Blade 에서는 `{{ }}` 출력에 이스케이프가 **기본으로 적용**된다

> 출처 — [Laravel 13.x · Blade](https://laravel.com/docs/13.x/blade#displaying-data)
> "Blade's `{{ }}` echo statements are automatically sent through PHP's `htmlspecialchars` function to prevent XSS attacks."

### 6) 글 조회와 404 처리 — 9줄 → 매개변수 1개

- **레거시**

```php
$id = get_int('id', 0);
$post = get_post($id);
if ($post === null) {
    $pageTitle = '글을 찾을 수 없음';
    require __DIR__ . '/../includes/header.php';
    echo '<p>존재하지 않는 글입니다. <a href="/">홈으로</a></p>';
    require __DIR__ . '/../includes/footer.php';
    exit;
}
```

- **Laravel**

```php
public function show(Post $post)   // URL 의 번호로 글을 조회해 전달한다. 없으면 404
```

> 출처 — [Laravel 13.x · Routing](https://laravel.com/docs/13.x/routing#route-model-binding)
> "Laravel will automatically inject the model instance that has an ID matching the corresponding value from the request URI. If a matching model instance is not found in the database, a 404 HTTP response will automatically be generated."

### 7) 삭제된 글 제외 — `deleted_at IS NULL` 20곳 → 1줄

- **레거시** — 글을 조회하는 SQL 마다 조건 작성

```sql
WHERE p.id = ? AND p.deleted_at IS NULL
```

- **Laravel** — 모델에 선언

```php
use SoftDeletes;
```

- 새 조회 코드를 작성할 때 **조건 누락으로 삭제된 글이 노출되는 오류**가 발생하지 않는다

> 출처 — [Laravel 13.x · Eloquent](https://laravel.com/docs/13.x/eloquent#soft-deleting)
> "When querying a model that uses soft deletes, the soft deleted models will automatically be excluded from all query results."

### 8) 게시판 페이징

- **레거시** — 글 전체를 조회한 뒤 PHP 배열에서 자른다

```php
$posts = get_posts();                                        // 190개 전부
$posts = filter_posts_by_work($posts, $work);
$posts = sort_posts($posts, $sort);
$totalCount = count($posts);
$totalPages = max(1, (int)ceil($totalCount / $perPage));
if ($page > $totalPages) { $page = $totalPages; }
$pagePosts = paginate_posts($posts, $page, $perPage);        // array_slice
// + 이전 · 페이지 번호 · 다음 링크를 출력하는 화면 코드 18줄
```

- **Laravel** — DB 에서 **해당 페이지 분량만** 조회한다

```php
$posts = Post::where('media_id', $media->id)->paginate(15);
```

```blade
{{ $posts->links() }}
```

> 출처 — [Laravel 13.x · Pagination](https://laravel.com/docs/13.x/pagination#paginating-query-builder-results)
> "The `paginate` method automatically takes care of setting the query's "limit" and "offset" based on the current page being viewed by the user."

## 슬라이드 E. 프레임워크 기본 동작과 프로젝트 규칙이 충돌한 사례

자동 처리는 **Laravel 의 규약**을 따른다. 프로젝트 규칙이 규약과 다르면 별도 설정이 필요하다.

- **`(수정됨)` 표시 오류**
  - 프로젝트 규칙 — `edited_at` 은 **수정한 적이 있을 때만** 값을 가진다
  - Laravel 기본 동작 — 수정 시각 컬럼을 **생성 시점에도** 채운다
  - 조치 — 글 생성 시 해당 컬럼을 비워 두는 처리를 모델에 추가했다
- **페이지 번호 스타일 불일치**
  - `{{ $posts->links() }}` 의 기본 HTML 은 Tailwind CSS 기준이라 프로젝트 CSS 가 적용되지 않았다
  - 조치 — 기존 마크업으로 페이지 번호 뷰를 작성하고 기본 뷰로 지정했다
  > 출처 — [Laravel 13.x · Pagination](https://laravel.com/docs/13.x/pagination#customizing-the-pagination-view)
  > "By default, the views rendered to display the pagination links are compatible with the Tailwind CSS framework. However, if you are not using Tailwind, you are free to define your own views to render these links."
- **정리** — 자동 처리 기능은 **무엇을 대신 처리하는지 확인한 뒤** 사용해야 한다
  - 뒤의 ③ 그래도 남은 것 · ④ 화면으로 이어진다
